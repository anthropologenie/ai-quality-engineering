## 2. Work Package 2 — Record Enrichment

Two fields added to every Retrieval Evaluation record:

| Field | Derivation |
|---|---|
| `expected_document_ids` | sorted, de-duplicated documents backing `expected_chunk_ids` |
| `observed_document_ids` | sorted, de-duplicated documents backing `observed_chunk_ids` |

**Additive, verified mechanically.** `test_enrichment_leaves_every_pre_existing_field_unchanged` builds the same entry with and without the mapping and asserts the two records differ by exactly the two new keys and in no other field's name, type, or value.

**No I/O was added.** `evaluate()` and `evaluate_entry()` take an optional `chunk_documents` mapping supplied by the orchestrator, which already built it via `index_chunk_documents()`. `evaluation/retrieval_evaluation.py` still performs no filesystem or network I/O, preserving the read-only property its module docstring claims.

**Ordering.** Both fields are sorted by document id, the convention every other id list in the module follows, and both are covered by the existing `stable ordering` check rather than by a new one — which would have changed that suite's reported check names and broken an existing specification.

**Unresolvable chunk ids raise** rather than being dropped. Silently omitting one would understate the document set — the field a Knowledge-stage diagnosis depends on — and would do so invisibly.

**Absent mapping yields empty lists, never absent keys**, so every consumer can read the fields unconditionally and a record predating the enrichment behaves exactly as it did before.

All existing P3.3.2 specifications pass unmodified. Nine new specifications were added for the two new fields (presence, derivation, de-duplication, sorted order, empty observed retrieval, absent mapping, unresolvable id, additivity, corpus coherence).

One shared **fixture** was updated — `evaluations` now supplies the mapping, matching what `scripts/evaluate_retrieval.py` produces. No assertion changed; every specification reads the same fields it read before.

## 4. Work Package 4 — Diagnosis: Rule Activation

### The determination the sprint asked for

> *"check whether 'wrong' is now determinable, or only 'which document'"*

**Only "which document."** Neither Knowledge rule was activated, and `evaluation/altm_rules.py` was **not modified at all** — no rule text, no `REACHABLE_STAGES` change (Knowledge was already listed as reachable in principle; it is the rules that could not fire).

| Rule | §5 symptom | Determination |
|---|---|---|
| `ALTM-KNOWLEDGE-1` | "Answer cites the wrong document version" | **Not activated.** The new fields establish which document was retrieved, never which version is current. Deciding a document is the *wrong version* of another requires the Knowledge Manifest — only its filenames encode `v2_2`/`v2_3` — which the dependency rule bars this engine from reading, plus canonical-document designation, which this sprint places out of scope. |
| `ALTM-KNOWLEDGE-2` | "Stale answer despite a recent source update" | **Not activated, and now excluded.** Its documented detection is *"Verify re-indexing was triggered on the source change."* `expected_document_ids` is non-empty and resolves through chunk ids Sprint P3.3.2 validated as present in the committed Chunk Corpus, so the expected document demonstrably **is** indexed. The row's premise is contradicted by evidence, not merely unverifiable. |

### What was activated

`ALTM-RETRIEVE-1` — *"Right topic, wrong specific document retrieved"* — a §5 row that had never fired because nothing distinguished it from `ALTM-RETRIEVE-2`. Zero-recall questions now split:

```
recall == 0 and expected ∩ observed documents = ∅   ->  ALTM-RETRIEVE-1
recall == 0 otherwise (expected document reached)   ->  ALTM-RETRIEVE-2
```

`ALTM-RETRIEVE-1` precedes `ALTM-RETRIEVE-2` in §5, so the split obeys the same document row order every other selection follows. Without document identity, behaviour is byte-for-byte what it was before this sprint — the split is additional resolution, not a changed rule, and `test_rule_selection_is_unchanged_without_document_identity` pins that.

### Confidence

A non-empty `expected_document_ids` excludes both upstream stages on evidence: **Knowledge**, because the expected document is in the corpus and indexed — exactly what `docs/altm.md` §4's Knowledge check tests — and **Index**, because its chunks exist by Sprint P3.3.2's validated referential integrity. With `docs/altm.md` §7's upstream-exclusion requirement satisfied, the Retrieve attribution has nothing above it unresolved: **Complete Evidence**.

This is uniform by consequence, not by construction. The same rule applied to a corpus that did not contain the expected document would exclude nothing and fall through to the pre-P3.3.5 assessment, which `test_confidence_is_unchanged_without_document_identity` pins.

### Existing specifications changed

**Exactly one**, and it grew by one appended row:

| Specification | Change | Justification |
|---|---|---|
| `test_committed_corpus_validation_report_is_all_pass` | added `"document identity integrity"` to the asserted check-name list | The validator gained a check, so the reported list grew. No assertion about pre-existing behaviour was weakened, and no limitation-specific assertion was removed — none existed. |

No specification asserting "Knowledge-stage diagnosis cannot be derived" existed to update: P3.3.4 recorded that limitation in its report rather than freezing it as a specification, which is why the capability could be added without retracting an assertion.

## 7. Implementation Observations

1. **The enrichment resolved the ambiguity against the Knowledge stage, not toward it.** The decision memo anticipated that document identity might let previously Insufficient questions attribute to Knowledge. It did the opposite: knowing the expected document is present in the corpus *excludes* the Knowledge stage, because `docs/altm.md`'s Knowledge failure mode is a corpus that does not contain the current version. This corpus contains both.

2. **The v2.2/v2.3 dominance finding is now localized to the Retrieve stage.** Three questions retrieved only Resume v2.2 while expecting Resume v2.3 and are diagnosed as `ALTM-RETRIEVE-1` (*"Right topic, wrong specific document retrieved"*). Five questions reached the expected Resume v2.3 document but returned none of its expected chunks and are diagnosed as `ALTM-RETRIEVE-2`. The documented investigations therefore localize the observed behaviour to retrieval-stage candidate selection and within-document chunk selection, without asserting a unique retrieval mechanism. The pattern carried from P3.3.1 through P3.3.4 as unattributed; it is now attributed to a stage, not to a mechanism.

3. **Confidence is now constant across the corpus.** All 22 questions are Complete Evidence, so the field discriminates nothing here — the degenerate opposite of the P3.3.4 state, where it mirrored classification exactly. In both cases it carries no information beyond what other fields already state, for opposite reasons.

4. **Five questions reached the expected document and still returned none of its expected chunks.** `ALTM-RETRIEVE-2` now means something narrower than it did in P3.3.4: not "retrieval missed the document" but "retrieval reached the right document and selected the wrong chunks within the corpus."

5. **Whether v2.2 belongs in the corpus at all is untouched.** That is a corpus-composition question — canonical document marking — explicitly out of scope, and not an ALTM stage failure under `docs/altm.md`'s definitions. No diagnosis produced here speaks to it.

6. **Document Recall is now derivable** from `expected_document_ids` and `observed_document_ids` without any dependency-rule change. It remains unimplemented by decision, not by limitation.
