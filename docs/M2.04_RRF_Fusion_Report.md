## 2. Engineering decisions

Recorded here as **engineering decisions, not Repository Owner authority** — the
same standing `sample_rag/retriever.py` records for `k1`, `b` and its IDF
variant. No repository authority states any of them.

| # | Decision | Reasoning |
|---|---|---|
| **E-1** | **`RRF_K = 60`** | The value introduced with the method — Cormack, Clarke & Buettcher, SIGIR 2009 — and the wider default. Chosen for the reason M2.03 chose conventional BM25 parameters: the ranking is the one a reader who knows RRF expects, and retuning is a visible change to a named constant. **Fixed before the benchmark was executed and not tuned against it** (§9) |
| **E-2** | **The seam is a pure function over two ranked id lists**, in a new `sample_rag/fusion.py` | Not a design preference — a constraint the repository already imposed. `tests/test_lexical_bm25.py::test_m203_the_semantic_route_is_untouched_by_the_lexical_one` permits exactly one borrower of the lexical route (`generator.py`), so a fusion module that imported either route would fail an existing specification. The smallest legal seam is a module that imports nothing |
| **E-3** | **No `HybridRetriever`, `FusionEngine` or orchestrator class** | Nothing varies behind such an abstraction. The same reasoning M2.03 recorded when it declined to invent a lexical Protocol to mirror `EmbeddingProvider` |
| **E-4** | **Tie-break = the P3.7.5 canonical ordering, passed in as `order`** | See §3. No authority governs post-fusion ties; M2.01C recorded the gap and named M2-04 as where it becomes real. The decision reuses the ordering the repository already has |
| **E-5** | **Duplicates within a route: first (best) occurrence wins** | Counting an id twice would let one route award a single candidate two contributions and outweigh the other — weighting by another name. Neither route emits duplicates today, so this is a definition, not a workaround |
| **E-6** | **Ranking is on the exact score, not a rounded one** | The opposite of M2.03's BM25 decision, deliberately. BM25 rounds because its score accumulates over many terms where float noise hides real collisions. An RRF score is a sum of at most two unit fractions in fixed order, so ties are already exactly reachable; rounding first could only *manufacture* ties. Specified by `test_m204_score_precision_is_a_reporting_constant_only` |
| **E-7** | **`top_k = 5` for both input routes and the fused output** | `evaluation/retrieval_metrics.py` defines K as the **observed retrieval size**, so unequal depths would compare two different metrics under one name. It is the repository's existing `DEFAULT_TOP_K`, restated rather than re-chosen. Searching over it is **M2-15** |
| **E-8** | **No exception type was introduced** | `k`'s positive domain is documented and unvalidated, exactly as `BM25Statistics.score` does not validate `k1` or `b`. An eighth flat exception type for an input no caller passes would add a failure surface with no caller |
| **E-9** | **Two new orchestrator scripts, not one** | `scripts/run_hybrid_retrieval.py` observes runtime behaviour; `scripts/compare_retrieval_routes.py` measures retrieval quality. The repository already separates these roles (`run_retrieval.py` / `evaluate_retrieval.py` / `report_retrieval_metrics.py`) |

## 3. RRF mathematical contract

```
RRF(d) = Σ  1 / (k + rank_r(d))      over the routes r that returned d
```

| Element | Contract |
|---|---|
| **k** | `60` (E-1) |
| **Rank base** | **1-based and positional.** A 0-based reading makes first place `1/k` instead of `1/(k+1)` — a different ranking function |
| **Input routes** | **Exactly two**, as two *named* parameters. A third route cannot be added by passing another argument; it requires editing the signature, which fails `test_m204_fusion_takes_exactly_two_routes` |
| **Input quantity** | **Positional rank only.** No BM25 score and no FAISS similarity reaches this module. Raw-score fusion is out of scope, and score normalization is what M2.03 deliberately removed |
| **Candidate universe** | The **UNION** of ids appearing in either route |
| **Unilateral candidate** | Fully eligible; carries that route's single contribution |
| **Missing id** | Contributes nothing. **No penalty term** — a penalty would make the score depend on how deep each route was asked to go |
| **Duplicate within a route** | First (best) occurrence fixes the rank; later occurrences contribute nothing (E-5) |
| **Empty semantic route** | Degenerates to the lexical order exactly (`1/(k+rank)` is strictly decreasing) |
| **Empty lexical route** | Degenerates to the semantic order exactly |
| **Both empty** | Returns `[]`. No exception |
| **`top_k <= 0`** | Returns `[]`, guarded explicitly — `candidates[:top_k]` is correct for `0` and silently wrong for `-1`, where Python would drop the *last* candidate and return everything else |
| **`top_k >` union size** | Returns the **whole union** in fused order. Truncation is all `top_k` does; it never pads |
| **`top_k` domain** | Counts over the **union**, so a fused result can be longer than either input |
| **Equal scores** | Broken by the ordering rule below |
| **Output identity** | `list[str]` of canonical `chunks[].id` — the shape `docs/architecture.md` §7 already fixes for the semantic route. **No `hybrid_chunk_id`, `fusion_id` or `retrieval_id`** |

### Tie-breaking, and its interaction with P3.7.5

Three levels, total over the candidate universe:

1. **RRF score, descending.**
2. **The canonical ordering authority** — position in a caller-supplied `order`
   sequence.
3. **First appearance** across the routes (semantic scanned first), for ids
   `order` does not cover; such ids sort *after* every id it does.

**Repository authority does not define post-fusion tie-breaking.** Sprint M2.01C
recorded exactly this gap: FAISS states no ordering among equal scores, no
authority states a tie-break for the vector route, and the question *"would
become a real question the moment a second route's results are fused with these
(**M2-04**)"* (`docs/M2.01C_…` §17). Level 2 is therefore an **engineering
decision (E-4)**, and the decision is to reuse the repository's existing
ordering rather than invent a second one.

**P3.7.5 is preserved, not replaced.** The lexical route's rule below the score
is *canonical documents ahead of superseded ones, then committed corpus
position*. Those two levels are a **total order over corpus chunks**, so
`scripts/run_hybrid_retrieval.py::canonical_order` materializes them as a single
sequence and passes it in. This keeps the fusion primitive a pure function while
letting the fused route inherit P3.7.5 exactly. **No alphabetical, hash-based or
unstable tie-break is used anywhere.**

Level 3 is **unreachable on the fused route** — both routes return ids drawn
from the committed corpus and `order` is that corpus. It exists to keep the
function total for a direct caller, the same reason `BM25Statistics.score`
defines an empty-corpus normalization ratio it can never meet through
`rank_candidates`.

## 4. Implementation

**`sample_rag/fusion.py`** — 3 public functions, **zero imports**.

| Function | Purpose |
|---|---|
| `positional_ranks(chunk_ids)` | `id → 1-based rank`, first occurrence wins |
| `rank_candidates(semantic_ids, lexical_ids, k, order)` | `(id, score)` pairs, best first |
| `reciprocal_rank_fusion(semantic_ids, lexical_ids, k, top_k, order)` | `list[str]` of canonical chunk ids |

The module imports **nothing at all** — not the routes, not FAISS, not the
embedding library, not `scripts/`, not even the standard library. That shape is
enforced by `test_m204_the_fusion_primitive_depends_on_nothing_at_all`, and it
is what makes M2-04 **structurally a consumer rather than a repair layer**: a
module that cannot reach either route cannot re-parameterize one.

**Criterion A-5's two standing exceptions did not widen.** No dependency was
added by this sprint at all.

## 6. Determinism

Same inputs + same `k` + same `top_k` + same corpus + same ordering rules →
the same ids in the same order. Nothing consults a clock, hash seed, environment
variable or random source; the fusion holds no state between calls.

Demonstrated by measurement, not asserted:

- `test_m204_repeated_identical_execution_produces_the_identical_ranking` — 10 runs, one distinct result.
- `test_m204_equal_rank_multisets_produce_bit_identical_scores` — asserted with `==` on floats, not `approx`, because `approx` would pass on the near-miss the specification exists to rule out.
- `test_m204_fusing_the_same_query_twice_returns_the_same_fused_order` — two independent runtimes, two independent index directories, the committed corpus, real BGE embeddings.
- `scripts/compare_retrieval_routes.py` executed twice produced byte-identical metrics.

| Index resolution (once per process) | |
|---|---|

## 10. M2.03-F-1 outcome — **CASE B: improved, but insufficient**

### CONCLUSION

**Two-route RRF materially and consistently improves retrieval quality over
BM25 alone — and over the semantic route alone — on every metric the repository
measures, but recovers only 28–43 % of the gap to the historical overlap
baseline. M2.03-F-1 remains PARTIALLY UNRESOLVED.**

**Evidence supporting the classification:**

1. **Improvement is real and uniform in direction.** RRF beats BM25 on Hit Rate
   (+0.0909), Chunk Precision@K micro (+0.0258), Chunk Recall@K micro (+0.0811)
   and No Match (−2). It beats the *semantic* route by the same margins. No
   measured metric moved against RRF.
2. **The residual gap is large.** Hit Rate remains 0.2273 below the historical
   baseline (−31.25 % relative); No Match is 11 against 6.
3. **The residual gap is not attributable to fusion.** The two-route candidate
   ceiling is 0.5455 Hit Rate, against a historical baseline of **0.7273**. RRF
   reached 91.7 % of that ceiling. **No two-route fusion of the current semantic
   and BM25 routes — at any `k`, any tie-break, any truncation rule — could
   reach the historical baseline on this benchmark**, because the evidence is
   not in the candidate pools to begin with.

**No repository-defined materiality threshold exists.** No committed authority
defines what "material improvement" means for a retrieval metric — verified by
inspection of `docs/architecture.md`, `docs/roadmap.md`,
`docs/AI_Quality_Metrics_Reference.md`, `docs/DEFERRED_ITEMS_REGISTER.md` and
`docs/ENGINEERING_TRACEABILITY_REGISTER.md`. **None was invented after seeing
the result.** The absolute and relative deltas and the direction are reported
above; whether they constitute "material improvement" is a Repository Owner
judgement this report does not pre-empt.

**The underlying BM25/chunk interaction did not disappear**, and this report
does not claim it did. F-1's mechanism — header-sized chunks interacting with
`b = 0.75` length normalization — is untouched by fusion, which reorders
candidates rather than changing which candidates BM25 produces.

### HYPOTHESIS vs FACT

| | Statement | Status |
|---|---|---|
| **FACT** | The RRF implementation computes `Σ 1/(k + rank)` correctly, deterministically, over the union, with the specified tie-break and edge-case behaviour | Established — 36 specifications, §7 |
| **FACT** | RRF measures 0.5000 / 0.1091 / 0.3243 against BM25's 0.4091 / 0.0833 / 0.2432 and the historical 0.7273 / 0.1481 / 0.4324 | Established — §8, reproduced twice |
| **FACT** | The two-route candidate ceiling on this benchmark is 0.5455 Hit Rate | Established — §8 |
| **HYPOTHESIS** | The residual gap is caused by chunk granularity and route quality rather than by fusion | **Supported but not proven** by the ceiling measurement. The ceiling proves fusion is not the *limiting* factor; it does not establish which of chunking, BM25 tuning or embedding quality dominates the remainder |
| **HYPOTHESIS** | A deeper per-route candidate pool would raise the ceiling | **Untested.** Deliberately not measured — that is parameter search against the benchmark, which §9's experimental discipline bars and which is **M2-15** |

### M2-15 and M2-17 were **NOT** triggered

RO-11 states they *"remain independently scoped … and neither is triggered
automatically by this entry."* **No BM25 parameter was tuned. No chunking was
changed. No tokenization was changed. No embedding was changed. No `k` search
was performed. No query rewriting or expansion was added.** This report
identifies where the remaining gap lives; allocating work against it is a
Repository Owner decision.

## 12. Findings

### **M2.04-F-1** — `test_m201c_the_runtime_artifact_is_not_a_repository_source_artifact` fails whenever the default-location vector index exists

**Severity: specification defect. Not introduced by this sprint's code; first
triggered by it.**

`tests/test_vector_query.py::test_m201c_the_runtime_artifact_is_not_a_repository_source_artifact`
asserts

```python
assert not (committed / FAISS_INDEX_FILENAME).exists()
assert not (committed / INDEX_METADATA_FILENAME).exists()
```

— **filesystem absence**, where its own docstring states the intent as *"generated
FAISS artifacts are **not committed**"* (RO-09 items 3–5). Those are different
properties. The artifact is `.gitignore`d, so it can be present on disk and
still not be a committed repository source artifact.

The test therefore passes only while **no one has ever executed
`VectorIndexRuntime` at its default location**. Every M2.01C specification uses
`tmp_path`, so nothing exercised the default path until now.
`scripts/run_hybrid_retrieval.py` is the **first repository path that runs the
runtime at `VECTOR_INDEX_ROOT`** — which is the location RO-09 item 9 and
M2.01C deliberately chose, precisely so the repository would have *"one runtime
location rather than two"*.

**Reproduction and isolation:**

| Step | Result |
|---|---|
| Full suite at `43df8f3`, no artifact | 558 passed |
| Full suite with M2-04, no artifact | **594 passed** |
| Run `scripts/run_hybrid_retrieval.py`, then full suite | 593 passed, **1 failed** |
| `rm -rf sample_rag/vector_index/`, re-run the single test | **passed** |

The failure is caused **solely by the presence of the derived artifact**, not by
any code change. No file authored by this sprint is involved.

**Disposition: NOT resolved by this sprint, deliberately.** Three remedies exist
and all three belong to the Repository Owner:

1. Amend the M2.01C specification to assert **Git tracking** (`git ls-files`) rather than filesystem presence — which is what its docstring already claims;
2. accept the artifact's presence as normal runtime state and narrow the assertion;
3. leave it and treat a populated runtime directory as a pre-test condition.

Editing a discharged sprint's governance-backed specification to accommodate
M2-04 is exactly what the sprint brief bars, so it was not done.

**Interim state:** the derived artifact was removed after measurement, so the
suite is green as delivered. It is untracked, `.gitignore`d and rebuildable —
RO-09 item 6: *"a caller who deletes it loses nothing but the time to rebuild"*
(rebuild cost measured at §9: 36.7 s).

### **M2.04-F-2** — `top_k` truncation can discard a correctly-ranked unilateral hit

**Severity: observation. Expected behaviour, recorded because it is measurable.**

On `f026_reasoning_01`, fusion returned 0 expected chunks where BM25 alone
returned 1 (§8). The expected chunk was scored and ordered correctly; it placed
7th in a 9-candidate union truncated to 5. Fusion widens the candidate pool
(7.55 ids per question) while the output depth stays at 5, so a unilateral
mid-rank hit can be displaced by the other route's higher-ranked candidates.

**Not remedied here.** The obvious remedy — raise the per-route or fused
`top_k` — is parameter search against the benchmark, which the sprint's
experimental discipline bars and which is **M2-15**. Recorded so the trade-off
is visible rather than discovered later. Net effect on this benchmark is
strongly positive: 1 loss against 5 recoveries and 1 above-both-routes gain.

### **M2.04-F-3** — semantic and lexical routes score an identical Hit Rate by coincidence

**Severity: observation.** Both routes measure Hit Rate 0.4091 (9 of 22), but
they are **not hitting the same questions** — §8 records three questions only
the semantic route reaches and two only BM25 reaches. Recorded so the identical
figures are not later mistaken for a wiring error in which one route's results
were fed to both columns. The per-question table is the disambiguating evidence.
