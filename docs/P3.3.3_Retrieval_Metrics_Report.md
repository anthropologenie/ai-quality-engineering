## 2. Metrics Engine

### Input contract

`evaluation.Record[]` — the records Sprint P3.3.2's `evaluate()` produces. Fields read:

| Field | Type | Used by |
|---|---|---|
| `id` | str | per-question row identity, duplicate detection |
| `classification` | str | classification counts and rates, Hit Rate |
| `expected_chunk_ids` | list | unique expected chunks, count/id agreement |
| `observed_chunk_ids` | list | unique retrieved chunks, count/id agreement |
| `matched_chunk_ids` | list | count/id agreement |
| `expected_count` | int | Chunk Recall@K denominator, micro recall denominator |
| `observed_count` | int | Chunk Precision@K denominator, micro precision denominator |
| `matched_count` | int | both numerators |

Records carrying additional fields are accepted — a later evaluation layer may record more than this engine measures.

### Output contract

`metrics.Report` — a nested mapping with three fixed sections and fixed key order:

```
{ "classification": {...},   # question counts and rates
  "retrieval":      {...},   # Hit Rate and chunk-level IR metrics
  "per_question":   [...] }  # one row per record, in record order
```

Every field is populated on every path; no field is ever `None`. Zero questions yields zero rates rather than an error, so the report is total.

### Dependency graph

```text
Retrieval Evaluation records
            │
            ├──────────────────────┐
            ▼                      ▼
   Metrics Engine          Independent Validator
   (Path A)                (Path B)
            │                      │
            ▼                      │
      metrics.Report ──────────────┤
                                   ▼
                          Validation report
```

The engine imports `math` and `collections` and nothing else. The validator imports `collections` and `fractions` and nothing else — in particular, nothing from the engine. Both are enforced structurally by AST-parsed allowlist specifications (`test_metrics_engine_imports_no_repository_authority`, `test_validator_imports_nothing_from_the_metrics_engine`), not by convention. Neither module performs filesystem or network I/O.

Only `scripts/report_retrieval_metrics.py` touches repository authorities, which Sprint P3.3.3 permits an orchestrator for integrity verification and for obtaining the engine's input.

## 3. Metric Definitions

### Classical IR metrics implemented in Milestone 1A

| Metric | Formal definition | Evaluation fields consumed |
|---|---|---|
| **Exact Match Rate** | `count(classification = Exact Match) / N` | `classification` |
| **Full Coverage Rate** | `count(classification = Full Coverage) / N` | `classification` |
| **Partial Match Rate** | `count(classification = Partial Match) / N` | `classification` |
| **No Match Rate** | `count(classification = No Match) / N` | `classification` |
| **Hit Rate** | `count(Exact Match) + count(Full Coverage) + count(Partial Match) / N`, equivalently `1 − No Match Rate` | `classification` |
| **Chunk Precision@K** (per question) | `\|E ∩ O\| / \|O\|` — `matched_count / observed_count` | `matched_count`, `observed_count` |
| **Chunk Precision@K** (macro) | mean of the per-question values | as above |
| **Chunk Precision@K** (micro) | `Σ matched_count / Σ observed_count` | as above |
| **Chunk Recall@K** (per question) | `\|E ∩ O\| / \|E\|` — `matched_count / expected_count` | `matched_count`, `expected_count` |
| **Chunk Recall@K** (macro) | mean of the per-question values | as above |
| **Chunk Recall@K** (micro) | `Σ matched_count / Σ expected_count` | as above |

`N` = questions evaluated. All rates are fractions in `[0.0, 1.0]`, not percentages, rounded to 4 places — the repository's established serialization precision (`scripts/run_retrieval.py` `corpus_utilization`, `evaluation/retrieval_evaluation.py` `_ratio`).

**Hit Rate is computed by aggregating Retrieval Evaluation classifications, not by re-performing set intersection** (Repository Decision 1). Sprint P3.3.2 already decided, validated and froze which questions overlap; intersecting again in the metrics layer would be a second implementation of that decision, free to drift from it. The term "Top-k Success Rate" is absent from the repository and no alias is retained.

**Macro and micro are both published.** No repository authority selects between them, and they answer different questions: macro weights every question equally, micro weights every chunk equally. Selecting one here would make a methodological choice on Sprint P3.3.4's behalf while presenting it as a measurement.

Macro values are means of the **unrounded** per-question ratios, rounded once at publication, so no figure is a mean of already-rounded numbers. `math.fsum` is used so the accumulation is correctly rounded regardless of record order.

### Canonical Ragas retrieval metrics — reserved for Milestone 2

| Metric | Status |
|---|---|
| **Context Precision** | **Not implemented.** Reserved for Milestone 2, Ragas. |
| **Context Recall** | **Not implemented.** Reserved for Milestone 2, Ragas. |

`docs/AI_Quality_Metrics_Reference.md` §Layer 3 names these two as *the* canonical retrieval metrics with "no substitutes at this layer", and §Milestone Mapping places Layer 3 in Milestone 2, once real embeddings, FAISS and generation exist.

**Chunk Precision@K and Chunk Recall@K are not those metrics.** They are deterministic set-arithmetic measurements over a committed evaluation. They do not approximate Ragas metrics, are not a proxy for them, and must not be reported under their names. The distinction is enforced in the naming itself: every metric this engine publishes is prefixed `chunk_`, `hit_`, or a classification name — never `context_`.

### Divide-by-zero handling

| Denominator | Zero reachable? | Behaviour |
|---|---|---|
| `observed_count` (Precision@K) | Yes — a question retrieving nothing | `0.0` by documented convention: no expected chunk was among those retrieved, because none was. |
| `expected_count` (Recall@K) | No | `validate_records` refuses a record expecting zero chunks, inheriting the domain Sprint P3.3.2's `evaluate_entry` already enforces. |
| `N` (all rates, macro) | Yes — an empty evaluation | `0.0`, keeping the report total. |
| `Σ observed_count`, `Σ expected_count` (micro) | Only when `N = 0` | `0.0`. |

**Note on the two structural identities (Sprint P3.3.3-R finding R-1).** `rate denominator integrity` and `hit rate complement identity` both re-derive classifications from the chunk sets via `_classify`, which is total and returns No Match exactly when the intersection is empty. `no_match ≡ N − hits` therefore holds identically, and neither check can fail: 4,000 randomized record sets plus the empty case produced zero failures, as the algebra requires. They document the identities Repository Decision 1 asserts; they are not contingent tests, and their PASS rows should not be read as independent evidence. The substantive verification of Hit Rate is performed by `independent derivation agreement`, which a mutation review confirmed does fire — corrupting `hit_rate` or `hit_count` by one is caught. Strengthening or reclassifying these two rows is deferred; no metric value depends on them.

**Specification suite: 171 passed** (136 pre-existing, 35 added). Two consecutive executions of `python3 -m scripts.report_retrieval_metrics` produced byte-identical stdout.

### Independence of the two derivation paths

Path B does not read `metrics.Report` to produce any value — the report is an argument to `compare()` alone, after every recomputed value already exists. Independence is structural on four axes:

1. **No import** from `evaluation.retrieval_metrics` — not its functions, constants, or rounding precision, all of which are restated. Enforced by an AST allowlist specification.
2. **Different input path** — every count is recomputed from `expected_chunk_ids` and `observed_chunk_ids` by set arithmetic; the records' `*_count` fields are read only to be checked, never to produce a metric.
3. **Different classification path** — each classification is re-derived from the chunk sets rather than read from `classification`.
4. **Different numeric path** — exact `fractions.Fraction` rational arithmetic, converted and rounded once at the end, against the engine's binary floating-point division throughout.

Agreement is exact equality of published values, not equality within a tolerance: both paths round to the same precision, so any tolerance would admit a real disagreement in the digits the report shows.

**Hit Rate is where the paths deliberately part company.** The engine aggregates Sprint P3.3.2's stored classifications (Repository Decision 1); the validator derives success from `|E ∩ O| > 0` directly. On consistent records the two agree; on a record whose label contradicts its sets they disagree, and the disagreement is the finding (`test_independent_validator_detects_a_wrong_classification`).

### A defect found and corrected during implementation

The `rate denominator integrity` check initially compared the sum of the four **published** rates against 1.0, and failed: `0.0 + 0.4545 + 0.1818 + 0.3636 = 0.9999`. Ten, four and eight twenty-seconds each round down. The residual is a property of rounding four numbers for display, not of the denominators, and a check that failed on it would be checking presentation. The check now sums exact rationals, where the identity holds exactly. The published rates still sum to 0.9999, which is correct and expected.

## 6. Implementation Observations

Inputs to Sprint P3.3.4 only. No diagnosis, no explanation.

1. **Document Recall is deferred.** *Document Recall is deferred because it is not derivable from Retrieval Evaluation records under the current dependency contract. This is an architectural limitation rather than an implementation defect.* Retrieval Evaluation records intentionally expose `expected_chunk_ids`, `observed_chunk_ids` and `matched_chunk_ids`, and intentionally do not expose document identifiers; computing Document Recall would require consulting the Chunk Corpus, the Evidence Trace Dataset, or the Retrieval Runtime, which the frozen dependency rule bars. The Retrieval Evaluation schema was not extended and Sprint P3.3.2 was not reopened. Note that Sprint P3.3.2's own aggregate summary does report expected and observed document distributions, derived at a layer that is permitted to read the corpus.

2. **"Top-k Success Rate" does not exist in this repository.** Hit Rate is the implemented metric, per Repository Decision 1. No alias is retained. Two docstring occurrences of the term in P3.3.2 code were corrected (§7).

3. **K is not carried in Retrieval Evaluation records.** The retriever's `top_k` is a runtime filter value in `RetrievalResult.diagnostics`; records do not carry it, and the dependency rule bars the engine from reading the runtime. Chunk Precision@K therefore divides by `observed_count` — what was actually retrieved — which equals the configured `top_k` for every question except `meta_qa_resume_f008_lexical_01`, whose corpus offered fewer candidates than `top_k` (2 retrieved).

4. **Precision is bounded above by `expected_count / top_k` for most questions.** 21 of 22 entries expect fewer than 5 chunks — the `expected_count` distribution is `{1: 15, 2: 4, 4: 2, 5: 1}` — while 21 of 22 retrieved exactly 5. Ten questions achieve recall 1.0 at precision 0.2.

5. **Macro and micro diverge in opposite directions for the two metrics.** Precision: macro 0.1273 below micro 0.1308. Recall: macro 0.5227 above micro 0.3889. Both aggregations remain published; no repository authority selects between them.

6. **Zero Exact Match makes Exact Match Rate 0.0.** With `top_k` fixed at 5 and 21 entries expecting fewer than 5 chunks, the category is structurally unreachable for those entries under the current configuration.

7. **The published classification rates sum to 0.9999, not 1.0.** Independent rounding of 10/22, 4/22 and 8/22. The exact rates sum to exactly 1, verified by `rate denominator integrity`.

8. **Hit Rate 0.6364 and Chunk Recall@K micro 0.3889 measure different populations.** The first counts questions with any relevant evidence; the second counts expected chunks retrieved. Both are published; neither is a restatement of the other.

No cause, explanation, or remedy for any of the above is offered. Diagnosis belongs exclusively to Sprint P3.3.4.
