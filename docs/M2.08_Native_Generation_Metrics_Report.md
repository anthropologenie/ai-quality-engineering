## 3. The four metrics, as implemented

Exactly the frozen semantics. Every unit, evidence frame and aggregation below is `docs/M2.08_Metric_Semantics_Report.md` §6, not a fresh derivation.

| Metric | Unit | Evidence frame | Numerator | Denominator |
|---|---|---|---|---|
| **Faithfulness** | one claim of `answer_text` | the **whole** assembled context | `SUPPORTED` | every claim |
| **Groundedness** | one claim of `answer_text` | **one passage**, in isolation | ∃ passage supporting it alone | every claim |
| **Hallucination Rate** | one claim of `answer_text` | the **whole** assembled context | `NOT_SUPPORTED` ∪ `CONTRADICTED` | every claim |
| **Answer Relevancy** | the **whole answer** | **the question** | `DIRECT` ∧ `COMPLETE` ∧ `ONLY` | every measured answer |

**Macro and micro are both published** for the three claim-level metrics — `docs/P3.3.3_…` §3's position, unchanged by the metric's name, and RO-18 Decision 8 prescribes no aggregation formula. For Answer Relevancy the unit is the answer and there is one per case, so **macro and micro coincide and one figure is published**; `test_m208_relevancy_publishes_one_figure_and_the_three_conjunct_counts` asserts that no second key is invented.

**Hallucination Rate is computed from the claim classifications, never from Faithfulness's value.** The support vocabulary has **four** verdicts, and the fourth is load-bearing: `PARTIALLY_SUPPORTED` is neither faithful nor hallucinated, so `faithfulness + hallucination_rate ≤ 1` with equality exactly when no claim is partially supported — which is `docs/altm.md` §6's *"near-complement … not guaranteed to sum to 100% once partial/ambiguous claims exist"*, made arithmetic.

### 3.1 The claim set comes from `answer_text`

`claim_prompt(question, answer_text)` has **no parameter** for the context, `statements` or `supporting_evidence`. Under `docs/GENERATION_CONTRACT.md` v2.0.0 the answer may be synthesized (§24.3) and §25.1 point 2 removes §8.1's requirement that it contain nothing outside the statements, so a claim asserted only in `answer_text` would otherwise go unmeasured — which is exactly where a fabrication would live.

### 3.2 Groundedness isolation, and the batching decision

`attribution_prompt(claim, passage)` receives **one passage**. Batching was considered and **declined**: the frozen report §9 fixes P3's inputs at *one claim and exactly one passage*, and every batching form available widens one of the two — batching passages defeats the isolation the metric is, and batching claims exposes each judgement to claims it was not asked about.

**One optimization is taken**: the scan stops at the first passage that carries the claim. Grounding is an existential, so a later passage cannot change the verdict; this spends strictly fewer judgements and **changes no judgement's inputs**. An ungrounded claim is still judged against every passage, so the negative case — the expensive one — carries complete evidence.

### 4.2 The invariant

`Grounded(claim) ⇒ Faithful(claim)`, therefore `groundedness ≤ faithfulness`, asserted across the probe set. The forbidden combination is **recorded, not repaired**: repairing it would fabricate a verdict and raising would discard a whole evaluation over one judgement, so each claim carries `instrument_inconsistency` and the report carries `instrument.grounded_but_not_faithful` — the diagnostic route `docs/M2.07_…` §9 used when two metrics contradicted each other.

## 5. Judge-input isolation — the boundary specifications

RO-18's isolation requirements are statements about what a judge was **shown**, and **a metric value cannot witness them**: a Groundedness figure computed from prompts carrying the whole context looks identical to one computed correctly. The scripted judge therefore **records the proposition and the exact prompt of every invocation**, and these six specifications inspect those prompts.

| Proposition | Receives | Asserted **not** to receive |
|---|---|---|
| **P1** claims | question, `answer_text` | assembled context, any passage, any chunk id, any support verdict, the joined context block |
| **P2** faithfulness | one claim, **the whole context joined by `CONTEXT_SEPARATOR`** | the question, `answer_text`, any chunk id |
| **P3** groundedness | one claim, **exactly one passage** | **every other passage** (checked per call), the joined context, the question, `answer_text`, chunk ids, P2's `PARTIALLY_SUPPORTED` / `CONTRADICTED` vocabulary |
| **P4** relevancy | question, `answer_text` | any passage, any chunk id, any support verdict, the claim |

Two further specifications support them: the exclusions are also asserted **at the signature** (`inspect.signature` — no proposition takes a reference answer, an attribution, a prior verdict or a case), and each proposition's opening line is pinned so the recording judge's routing cannot silently drift.

The judge double additionally **raises if a P2 or P3 prompt matches more than one claim**, so claim-level isolation is enforced by the instrument rather than only asserted.

## 7. Judge injection and the deterministic / live boundary

The engine takes `judge(prompt: str) -> str` and holds no provider concept — the seam `evaluation/context_metrics.py` established and **RO-18 Decision 4** names for M2-08: *native M2-08 evaluator → injected judge seam → existing provider boundary*.

```text
deterministic     scripted judge  ->  engine  ->  structured metric result   (pytest)
live              DeepSeek judge  ->  engine  ->  evaluation evidence        (on demand only)
```

**RO-14 Decision 2, carried forward by RO-18 Decision 6, holds structurally**: there is nothing in the engine or the specification file for a test to reach a network through, and `test_m208_no_specification_can_reach_a_provider` asserts it rather than leaving it to reading.

**Determinism boundary, stated rather than assumed.** Everything except the judge's answers is deterministic. The judge's answers are not, **the claim denominator is itself a judge product**, and the object being measured is an `answer_text` that **G-9** under v2.0.0 does not require to be reproducible. No figure this engine produces is deterministic, and the entry point prints that alongside the numbers.

### 7.1 Credential and payload discipline

`DEEPSEEK_API_KEY` is consumed by `sample_rag/deepseek.py` from the process environment and **nothing in this sprint reads it**. Verified by AST across all three new files: **zero** accesses to `environ` or `getenv`, and **zero** credential literals in code. The single textual occurrence is one docstring line in `scripts/evaluate_generation.py` recording that the script never reads it — the same form `scripts/evaluate_context.py` already uses.

`GenerationMetricsError` **never quotes a judge response**: a verdict that could not be read is reported by the *proposition being judged* — case id, claim index, passage id — so an evaluation failure can be pasted into a report safely. `test_m208_a_failed_judgement_never_quotes_what_the_judge_returned` asserts it.

No raw request payload, raw response payload, authorization header or provider metadata is returned by the engine or printed by the entry point, so there is nothing to suppress.

## 8. Circularity — what is refused, not merely unused

`validate_case` **refuses** a case carrying any of `statements`, `supporting_evidence`, `expected_answer`, `reference_answer`, `expected_chunk`, `expected_metrics`. Six parametrized specifications assert each refusal.

**A refused input is stronger than an unused one**: a later caller cannot pass one by accident, and no proposition has a parameter it could reach a judge through.

`docs/GENERATION_CONTRACT.md` §24.3 guarantees where a `SupportingEvidence` **came from**, not that the claim it is attached to is entailed by it, and §25.1 closes the inference — *"that a synthesized `answer_text` is permitted is not a statement that it is faithful."* Reading the system's own attribution as the reference would convert a structural guarantee into the empirical property M2-08 exists to measure.

The system's attribution **is** retained: `scripts/evaluate_generation.py` prints the `statements` count and the cited chunk ids in a section labelled *"diagnostic only, not a metric reference"*, so a reader can compare what the system cited against what the judge found without either being mistaken for the other. It never enters a case.

**The golden `expected_answer` is read by nothing.** Three golden fields are used: `id`, `question`, and `expected_outcome` for printed dataset composition only. **The Abstain partition is taken from the observed `GenerationResult.outcome`**, not from the expectation — the domain statement is about whether the system asserted anything.

## 9. Abstention

`docs/GENERATION_CONTRACT.md` **G-8** and §9.3: the abstention text *"asserts nothing about the corpus"* and `statements` is empty exactly then. An `Abstain` case therefore carries **no claims**, and:

- the three claim-level metrics carry `None` with a documented reason — **not `0.0`**, because an absent denominator is not a measurement of zero;
- **no judge call is made** on an Abstain case (asserted: `judge.calls == []`);
- Answer Relevancy carries `None` and the **U-3** reason verbatim;
- aggregates publish `cases_evaluated`, `cases_measured` and `cases_without_claims` / `cases_undefined` side by side, so both figures can be read against the number of cases that had a denominator.

This deliberately differs from `evaluation/context_metrics.py`, which returns `0.0` in its analogous place — and the difference is the point. There, an empty retrieval genuinely recovered nothing, so zero was a measurement. **U-3 is not silently resolved.**

## 11. Live evaluation — what was and was not run

**The full 22-case live evaluation was NOT executed, and that is a deliberate stop.**

`scripts/evaluate_generation.py` evaluates the whole golden dataset in one run, which is roughly **22 generation calls plus ~450 judge calls**. Running it produces a headline score, and the sprint instruction is explicit that a live evaluation must not be run automatically to obtain one. **Whether to spend that run is the Repository Owner's decision, not this sprint's**, and nothing in the acceptance criteria depends on it.

**What was verified live: that the authorized boundary is reusable, with one call.**

| | |
|---|---|
| Calls made | **1** |
| Adapter | `DeepSeekClient.complete(messages) -> str` → `judge(prompt) -> str`, the identical two-line adapter `main()` declares |
| Model | `deepseek-v4-flash` |
| Proposition | P2 support, one claim against one context |
| Returned verdict | `SUPPORTED`, parsed cleanly against the closed four-verdict vocabulary |
| Executed from | a scratch file outside the repository — **no repository artifact, no persisted output** |
| `sample_rag/deepseek.py` | unmodified before and after (digest unchanged) |

**RO-18 Decision 4's condition is satisfied and the finding is that nothing had to change**: no subclass, no wrapper, no second client, no SDK, no router, no session, no retry, no HTTP primitive and no credential passing through the evaluation layer. The provider architecture is byte-identical.

The pipeline half was verified without any provider call: over three real golden questions, real hybrid retrieval and real `ContextBuilder` assembly produce passages whose `CONTEXT_SEPARATOR` join is **byte-identical to `Prompt.context`**, and the resulting cases pass `validate_case`. The entry point checks that equality at runtime and raises rather than measuring a frame that is not the prompt the model saw.

## 12. Findings carried forward

**None blocks the implementation, and none was resolved by it.** Each was recorded in the frozen semantics report and is restated here because an implementation now exists that a reader will check against them.

**U-2 — Groundedness's claim domain.** `docs/AI_Quality_Metrics_Reference.md` and `docs/altm.md` §6 say *"every individual / each claim"*; `docs/glossary.md` and RO-18 D-8 say *"important / substantive"*. The implementation takes the invention-free reading — every claim P1 yields is in domain — because a narrower importance filter would need a standard the repository does not define. **Unchanged and still open.**

**U-3 — Answer Relevancy over an abstention.** Undefined by repository authority. Implemented as `None` plus the reason string, carried in the evidence and asserted by `…probe_ar8_…`. **Not filled.**

**U-4 — `Hallucination Rate` absent from the golden `expected_metrics`.** All 22 entries list the other four metrics and not this one. The dataset was **not modified**; the field is a per-question annotation, not a metric definition.

**M2-09 and M2-10 remain OPEN and separate.** M2-09 (Answer Relevancy, *Metric*) and M2-10 (Context Precision / Recall, *Metric*) are distinct capability rows. **RO-16 D-8, RO-17 D-7 and RO-18 D-10** all record that a sprint which measures is not thereby a sprint which discharges the measurement capability. **This sprint discharges nothing at all**, so no reading of it discharges either. RO-18 is silent on M2-09 specifically — recorded, not resolved.

**One instrument property to watch on a live run.** `groundedness ≤ faithfulness` holds by definition but is produced by two independent judgements, so a live run can violate it. That is an inconsistent instrument, not a result: the report counts it as `instrument.grounded_but_not_faithful` and the entry point prints it above the per-case rows. **A non-zero count on a first live run should be read the way `docs/M2.07_…` §9 read its own contradiction — as a proposition to re-examine, not a score to publish.**
