## 2. Existing Decisions

Sixteen findings are recorded as **D-1 … D-16** in `docs/GENERATION_CONTRACT.md` §2. The load-bearing ones:

**A Generation component already exists and is fully named.** `docs/architecture.md` §5 defines the `Generator` — responsibility, interface `generate(prompt: Prompt) -> Answer`, dependency on the Context Builder, status *"1A — deterministic stub generator"*, evolution *"DeepSeek API integration"*. `docs/glossary.md` assigns it the **Infer** stage. `docs/altm.md` §4 names the artifacts at each stage boundary: *Prompt*, *Raw Output*, *Delivered Output*. `docs/architecture.md` §6 already allocates the file `sample_rag/generator.py`.

**No Generation artifact schema exists.** `docs/MILESTONE_1A.md` build item 5 is one sentence and defines no fields. A repository-wide search finds no `GenerationResult`, no Generation dataclass, no `sample_rag/generator.py`, and no Generation schema in any committed authority. **There was nothing to supersede — only something to define.**

**The outcome vocabulary already exists and is already implemented.** `docs/roadmap.md` §2.4 defines `Answer / Abstain / Clarify`; `scripts/build_evidence_trace.py` implements `OUTCOME_ANSWER`, `OUTCOME_ABSTAIN`, excludes `Clarify` from Milestone 1A (Decision C), and maps the QA Dataset's `No Answer` category to `Abstain`. All 22 committed Evidence Trace entries already carry an expected outcome.

**Four ALTM rules already attribute failures to the Generator** — `ALTM-INFER-1` (hallucinated fact), `ALTM-INFER-2` (false confidence on an unanswerable question), `ALTM-INDEX-1` (contradictory answers across repeated runs), `ALTM-ASSEMBLE-1` (correct evidence, wrong answer). These are recorded repository failure modes, and the contract is shaped to make them unreachable by construction rather than detectable after the fact.

**Determinism is enforced in this repository by exclusion, twice, deliberately.** `created_at` was removed from the Knowledge Manifest because it *"would make the manifest non-deterministic"*; `retrieval_time_ms` is *"fixed at 0 rather than measured"*. Both precedents are binding on this contract.

**`RetrievalResult` is the shape precedent.** Four fields, deterministic placeholders in every one, never `None`, plus `diagnostics` as *"the contract's own open mapping"*. And build item 4 is the **governance** precedent: it superseded `docs/architecture.md` §5's `-> List[Chunk]` explicitly rather than diverging silently.

## 3. Contract Reconciliation

Everything the repository already defines is carried forward unchanged: the component name **Generator**, the **Infer** stage ownership, the artifact-boundary terminology, the outcome vocabulary **Answer / Abstain**, the `No Answer → Abstain` mapping (left in its existing owner, `derive_expected_outcome`), the runtime-artifact classification from `docs/CHUNK_CONTRACT.md` §5, the document-frame character-offset semantics from `docs/CHUNK_CONTRACT.md` §13, and the `diagnostics` open-mapping pattern from build item 4.

**Two places could not adopt existing text as written.** Both are raised as gaps under the Definition of Done's documented-gap route, with options and a recommendation, and **neither is resolved by this sprint** — the standing governance rule is explicit that *"an implementing agent presents options and a recommendation; a recommendation is not a decision."*

| Gap | Problem | Recommendation |
|---|---|---|
| **G-1** — artifact name | `docs/architecture.md` §5 names the return type `Answer`, and never defines it. The repository already uses the word "answer" in five distinct committed senses, one of which — the `Answer` **outcome value** — would sit *inside* the artifact, producing contract text of the form *"an `Answer` whose outcome is `Answer`"* | **`GenerationResult`**, mirroring `RetrievalResult`, with the word *answer* preserved as the field `answer_text`. Follows precedent D-6 exactly |
| **G-2** — input type | §5 specifies `generate(prompt: Prompt)`, but there is no Context Builder, no `Prompt` contract anywhere, and the Assemble stage is formally recorded as unreachable | **`generate(query: str, retrieval: RetrievalResult)`** — inside the permitted dependency boundary, introducing no new artifact, applying the same reasoning `reachable_stage()` already applies to unimplemented stages. §5's signature remains the Milestone 2 target |

Rejected alternatives are recorded with their reasons in `docs/GENERATION_CONTRACT.md` §6 — including the option of defining a `Prompt` contract here (rejected: it would design a different component's stage inside a Generation sprint) and of letting the Generator build its own prompt internally (rejected: it would silently absorb the Assemble stage, making `ALTM-ASSEMBLE-1` undiagnosable).

If G-1 is approved, `docs/architecture.md` §5's `Generator` row should be amended by the Repository Owner the way build item 4 amended the `Retriever` row. **This sprint did not make that amendment.**

## 4. Generation Semantic Contract

Three nested structures, `docs/GENERATION_CONTRACT.md` §7:

```text
GenerationResult                     GeneratedStatement          SupportingEvidence
├── answer_text          str         ├── text              str   ├── chunk_id        str
├── outcome              str         └── supporting_       list  ├── document_id     str
├── statements           list             evidence               ├── character_start int
└── diagnostics          dict                                    ├── character_end   int
                                                                 └── text            str
```

The nesting is the executable form of the sprint's evidence chain: statement → supporting evidence → chunk id → committed Chunk Corpus.

**The one substantive reconciliation.** Sprint guarantee 1 requires every statement to resolve to *"supporting facts"* — but `fact` is a committed dataset authority (`datasets/golden/resume_facts.json`) that the Runtime Dependency Boundary bars the Generator from reading. The contract names the runtime level `SupportingEvidence` and shows that both hold, because a Golden Dataset fact and a runtime evidence span **meet at the chunk id**:

```text
Golden Dataset fact ──GD-8──► document-frame span ──X-15──► chunk id ◄── SupportingEvidence
                                                               │
                                                           X-12: exists in the Chunk Corpus
```

`SupportingEvidence` **is** the runtime realization of a supporting fact — a citable span with a document-frame location, which is exactly what a Golden Dataset fact resolves to under `resolve_fact_chunks`. The runtime carries no dataset dependency; validation can still join the two, at the chunk id (§19.4 of the contract).

Also fixed: the outcome domain (§9), abstention semantics including the honest note that the evidence guarantees hold **vacuously** on the Abstain path (§9.3), traceability requirements T-1 … T-5 (§10), total orderings for both lists inherited from orderings the repository already froze (§11), and determinism by exclusion (§12).

## 5. Serialization Specification

The semantic model and the serialization form are kept separate: §7 is satisfiable by a dataclass, a JSON document, or a future representation, and specifying one serialization does not make the model depend on it.

| Aspect | Specification |
|---|---|
| In-memory | Frozen dataclasses, §7 field order — mirroring `RetrievalResult`'s `@dataclass(frozen=True)` |
| Serialized | `json.dumps(result, indent=2) + "\n"`, UTF-8, insertion-order keys, one trailing newline — the convention `write_manifest`, `write_chunks` and `write_evidence_trace` already share |
| Key order | Declaration order. Keys SHALL NOT be sorted: insertion order *is* the contract's order |
| Persistence | **None required or defined.** `GenerationResult` is a Runtime Artifact under `docs/CHUNK_CONTRACT.md` §5 — query-derived, single-request, not version-controlled |

Requiring byte-identical serialization without requiring persistence is deliberate: the property is what makes two runs comparable — by a test, a CLI diff, or a future regression harness — whether or not anything is written to disk.

## 7. Repository Guarantees

Fourteen normative SHALL statements, `docs/GENERATION_CONTRACT.md` §16. The sprint's seven required guarantees map as:

| Sprint guarantee | Contract |
|---|---|
| 1. Every statement resolves to supporting facts | **G-4** (with the fact/evidence reconciliation of §7.1) |
| 2. Every fact resolves to supporting chunks | **G-5** |
| 3. Every chunk exists in the committed Chunk Corpus | **G-6** — holds *by construction*: chunk ids are carried through from retrieval and never constructed by the Generator |
| 4. Support by construction; no entailment/hallucination/faithfulness/groundedness/claim verification | **G-7** |
| 5. Byte-identical repeated output | **G-9** |
| 6. Deterministic evidence ordering | **G-10** |
| 7. Full traceability to committed authorities | **G-12** |

Seven further guarantees close shape and boundary: artifact shape (G-1), outcome domain (G-2), answer non-emptiness (G-3), abstention exclusivity (G-8, `statements == []` **iff** Abstain), verbatim evidence (G-11), the runtime dependency boundary (G-13), and observational purity — no filesystem I/O, no network I/O, no mutation of the consumed `RetrievalResult` (G-14).

## 8. Validation Strategy

Deterministic repository validation only — pytest, stdlib, committed state. No DeepEval, no Ragas, no LLM judge, no embedding or semantic evaluation.

1. **Contract conformance (synthetic)** — one specification per invariant with a synthetic negative case each, following the pattern `tests/test_evidence_trace_dataset.py` established, including a control confirming the valid baseline is accepted.
2. **Runtime behaviour** — the Generator executed over the committed corpus via the Retriever; shape, invariants and the Answer/Abstain split asserted, **no particular answer text asserted**. Freezing today's answers would convert a future generation improvement into a test failure — the reasoning `tests/test_retrieval_evaluation.py` already records for retrieval classifications.
3. **Determinism** — two executions, field-for-field equality plus byte-identical serialization.
4. **Cross-authority validation** — at validation time only, where the §7.1 join is exercised: emitted chunk ids against the Chunk Corpus, document ids against the Manifest, evidence text verbatim at its offsets via `KnowledgeSource().load()`, and — **observationally, not as an equality assertion** — emitted chunk ids against the Evidence Trace `expected_chunk`.
5. **Mutation verification** — every load-bearing specification verified to fail when its invariant is broken, by P3.4.1's in-memory method.

**What validation does not do:** assert answer quality, relevance, fluency, or truthfulness. The Milestone 1A claim is narrower and fully checkable — *every claim the Generator makes is a verbatim quotation of committed corpus evidence, cited to the chunk and document it came from.*

## 10. Summary

### Sprint outcome

`docs/GENERATION_CONTRACT.md` is a complete, proposed repository authority: 22 sections defining the Generation semantic model, its serialization, its traceability matrix, fourteen normative guarantees, the runtime dependency boundary, the validation strategy, and the implementation readiness assessment. `docs/P3.5.1_Generation_Contract_Report.md` is this record.

**No implementation was written. No runtime behaviour changed. No repository authority was modified.** Two new documentation files; nothing else in the tree differs. The full suite passes at 297 as it did at sprint start.

### Observations

1. **The repository had more Generation design recorded than a single build item suggests.** Build item 5 is one sentence, but the component, its interface, its ALTM stage, its failure modes, its artifact-boundary names, its outcome vocabulary, its milestone status and even its implementation file were all already committed across five documents. The contract's substance is mostly reconciliation, not invention — which is the outcome the reconciliation mandate was designed to produce.

2. **The sprint's own guarantee wording collided with a committed dataset authority.** "Every generated statement resolves to supporting facts" cannot be read literally when `facts` is a barred runtime dependency. The chunk id turned out to be the join that satisfies both the guarantee and the boundary — and it works because P3.4.1 had already made `fact → chunk` an executable, verified relationship (GD-8, X-15, X-12).

3. **The naming collision on "answer" is a real repository condition, not a stylistic preference.** Five committed meanings, one of which would appear inside the artifact under the other's name. It is recorded as evidence under G-1 rather than resolved by fiat.

4. **Two of the four Generator-attributed ALTM rules become structurally unreachable** under this contract rather than merely detectable: a Generator that can only emit verbatim quotations cannot fabricate a claim (`ALTM-INFER-1`), and one whose outcome domain forces `Abstain` when it has nothing to quote cannot express false confidence (`ALTM-INFER-2`). That is a property of Milestone 1A's deterministic scope and will not survive the Milestone 2 DeepSeek swap — at which point those rules become live again, and the Layer 4 metrics exist to catch them.

5. **The `Prompt` gap is the one place where the frozen architecture and the implemented repository genuinely disagree**, and the disagreement predates this sprint: `docs/architecture.md` §5 has specified a Context Builder since Session 2, and no sprint has built one. This contract does not resolve that — it routes around it inside the permitted dependency boundary and records the §5 signature as the Milestone 2 target.

6. **Implementing the Generator will make the ALTM Infer stage reachable**, which `evaluation/altm_rules.py` `REACHABLE_STAGES` currently excludes. That is a Diagnosis-layer scope decision, not a side effect to be absorbed silently; it is recorded as Q-3 so a later sprint finds it rather than rediscovers it.
