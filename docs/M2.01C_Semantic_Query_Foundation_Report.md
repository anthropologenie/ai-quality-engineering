## 4. Query contract derived (Phase 1)

Every row states where the answer came from. Where an answer is an engineering decision rather than an authority reading, it says so — and each such decision is specified, so changing it is visible rather than silent.

| # | Question | Answer | Derived from |
|---|---|---|---|
| 1 | Input type | `list[float]`, exactly `identity.dimension` components | **Authority** — §7 / `vector_store.py` |
| 2 | `top_k` semantics | How many nearest neighbours to return; an upper bound, not a guarantee | **Authority** — *"the ids of the `top_k` nearest"* |
| 3 | Output type | `list[str]` — chunk ids | **Authority** — §7; ids are the join key `docs/CHUNK_CONTRACT.md` §17 makes unique and `sample_rag/retriever.py` already ranks on |
| 4 | Ordering guarantee | FAISS's own similarity order, **nearest first**, unmodified | **Authority** — *"nearest"* (§7 docstring); §5's *"ranked evidence"*. No re-ordering is applied |
| 5 | `top_k <= 0` | `[]` | **Engineering decision.** Total, invents no error type; the nearest existing behaviour (`retriever.py`'s slice-based top-k) is empty at zero |
| 6 | `top_k >` vector count | Every stored id, and no more | **Authority-consistent** — there are only *n* stored vectors, so *"the ids of the nearest"* cannot exceed them. FAISS's `-1` padding is dropped |
| 7 | Empty index | `[]` | **Authority-consistent** — `docs/CHUNK_CONTRACT.md` §11's *"zero or more"*, already legal at the Index stage |
| 8 | Wrong query dimensionality | `VectorIndexCompatibilityError` | **Engineering decision, reusing an existing exception.** `dimension` is an RO-08 Decision 3 signal and this exception already means *this index does not identify the inputs it is being used for*. **No new exception type was introduced** |
| 9 | Missing / stale / incompatible index | Rebuilt by the runtime lifecycle; never queried stale | **Authority** — RO-09 items 1–2, 8 |
| 10 | Ordinal → chunk_id | `identity.chunk_ids[ordinal]`, through M2.01B's `chunk_id_at` | **Authority** — M2.01B's recorded mapping; RO-08 Decision 3's ordered chunk-id set |
| 11 | Duplicate chunk ids possible? | **No.** FAISS returns each ordinal at most once; chunk ids are globally unique and DQ-2 / DQ-5 validate that. **No de-duplication is performed** | **Authority** — `docs/CHUNK_CONTRACT.md` §17; `docs/DATA_QUALITY_VALIDATION_PLAN.md` §8.1 |
| 12 | Ordering follows FAISS distance ordering? | **Yes**, without adjustment | **Authority-consistent** — any adjustment would be M2-03 / M2-04 / M2-05 |
| 13 | Similarity scores exposed? | **No — deliberately hidden.** `search` returns distances; they are discarded | **Authority** — the frozen return type is `list[str]`. Exposing scores would widen the contract, and their only consumer today would be the rank fusion this sprint may not implement |

**Unresolved but non-blocking:** FAISS's ordering among *exactly equal* similarities is not specified by FAISS and not specified here. It cannot arise from distinct stored vectors under exact flat search, and no repository authority states a tie-break for the vector route. Recorded as an observation (§17, F-3), not resolved.

### 6.3 The lifecycle

`sample_rag/vector_runtime.py` implements RO-09 item 8 in the order the ruling lists it:

```
canonical corpus
      |
      v
expected identity  ..............  identity_for(...), computed from the corpus
      |
      v
artifact exists? ------- no ----->  rebuild -> save        REBUILT_ABSENT
      |
     yes
      |
      v
load + cross-validate -- fails -->  rebuild -> save        REBUILT_ABSENT
      |                             (corrupt / half-written / files disagree)
      v
compatibility check ---- stale -->  rebuild -> save        REBUILT_STALE
      |                             (naming the differing signals)
   current
      |
      v
    query                                                  LOADED
```

**Two failure classes, one remedy.** `VectorIndexPersistenceError` (absent, half-written, unparseable, corrupt, self-inconsistent) and `VectorIndexCompatibilityError` (intact but built over other inputs) are both recoverable *at this layer only*, because RO-09 items 1–2 make the artifact derived and rebuildable: there is no state to lose and nothing for a caller to decide. Both still reach a caller who uses `sample_rag/vector_index.py` directly, where they mean what they always meant. They are caught **by class**, never bare, so a genuine defect in this repository's own code still surfaces as a defect.

**The lifecycle reports what it did.** `disposition` is `LOADED`, `REBUILT_ABSENT` or `REBUILT_STALE`, and `rebuild_signals` carries `VectorIndexIdentity.mismatches`' output unchanged — *a report rather than a bool*, the shape M2.01B and every W6 predicate in `tests/test_data_quality.py` already use.

### 6.4 Rebuild — no new corpus architecture

The rebuild path is three existing calls: `Indexer.index` → `FaissVectorIndex.build` → `FaissVectorIndex.save`. It therefore preserves chunk ordering, chunk ids, embedding configuration, index configuration and metadata identity **because it is the same code that built the first one**, not because this sprint reproduces their behaviour.

**The corpus is injected, not loaded here.** `docs/architecture.md` §6 bars `sample_rag/` from importing `scripts/`, and the Chunk Corpus and Knowledge Manifest are `scripts/`' artifacts. The runtime is handed its chunks and documents — exactly as `Retriever` is handed chunks and `FaissVectorIndex.build` is handed both. No corpus parsing exists in the query layer, and the duplication `docs/ENGINEERING_TRACEABILITY_REGISTER.md` §5 rates **High** risk was not created.

**Staleness costs no embedding.** `expected_identity()` needs the corpus, the model identity and the provider's *declared* width — none of which requires embedding anything. It reads the width through `Indexer(provider).index([])`, the stage that already owns the defensive read for a provider declaring none. Measured at **0.46 ms** against the committed corpus, versus **33 s** for the rebuild it exists to avoid. Specified by `test_m201c_staleness_is_checked_without_embedding_the_corpus`, which counts embed executions rather than elapsed time.

## 9. Query semantics

```python
def query(self, vector: list[float], top_k: int) -> list[str]:
    if top_k <= 0:
        return []
    if len(vector) != self._identity.dimension:
        raise VectorIndexCompatibilityError(...)
    _, ordinals = self._faiss_index.search(numpy.array([vector], dtype=numpy.float32), top_k)
    return [self.chunk_id_at(int(ordinal)) for ordinal in ordinals[0] if ordinal != -1]
```

Four behaviours, each specified:

1. **Non-positive `top_k` is answered, not raised.** *Engineering decision* (§4 row 5).
2. **Dimension is checked before FAISS sees the vector**, so the failure names the repository's fact rather than surfacing as a third-party assertion. *Engineering decision reusing an existing exception* (§4 row 8).
3. **`-1` padding is dropped rather than mapped.** This is the one line that would fail silently and plausibly if omitted: `chunk_ids[-1]` is the *last* chunk in Python, so an unfiltered mapping would return it repeatedly as if it were a neighbour. `test_m201c_top_k_larger_than_the_corpus_returns_only_what_is_stored` exists for exactly this.
4. **Distances are discarded.** The frozen return type is `list[str]`; scores are hidden deliberately, not incidentally (§4 row 13).

**Nothing re-orders, weights, normalizes, fuses or reranks what FAISS returns.**

## 12. Retrieval correctness evidence

A small controlled baseline, over three chunks from three plainly different subjects, embedded by the real `BGEEmbeddingProvider` at the pinned revision. **Not an evaluation framework** — no Ragas, no DeepEval, no Context Precision, no Context Recall, no scoring of quality. The question asked is only: *does the query path retrieve what the index says it should?*

| Query | Expected top-1 | Observed top-1 |
|---|---|---|
| *"Who managed a software testing team?"* | `s0` — *"Led a cross-functional QA team of five engineers…"* | **`s0`** ✅ |
| *"building data pipelines in python"* | `s2` — *"Built ETL data pipelines in Python…"* | **`s2`** ✅ |
| *"heavy seasonal rain near the sea"* | `s1` — *"Rainfall in the coastal region peaked…"* | **`s1`** ✅ |
| *"cross-functional quality assurance leadership"* | `s0` | **`s0`** ✅ |
| *"monsoon rainfall on the coast"* | **not** `s0` | **`s1`** ✅ |

The first query is the load-bearing one: it shares almost no vocabulary with the chunk it retrieves — *"managed"* / *"Led"*, *"software testing"* / *"QA"* — so it is retrieved by meaning, which the Milestone 1B digest could not have done and never claimed to.

**The contrast case is why the first three mean something.** Without `test_m201c_an_unrelated_query_does_not_retrieve_the_related_chunk_first`, "the expected chunk appeared" could be satisfied by an index returning the same order for every query. Two queries on different subjects rank different chunks first.

**Over the committed corpus** (259 chunks, 384 dimensions), `test_m201c_the_committed_corpus_answers_a_semantic_query` builds, persists, reloads and queries the real pipeline end to end: every returned id resolves to a real chunk, the requested `top_k` is honoured, the artifact holds one vector per chunk, and two queries on different subjects do not produce the same ranking. The assertions are about **the query path**, not about answer quality — judging *how good* retrieval is belongs to Ragas (**M2-07**) and is not attempted.

Stated as **relative ordering, never as a similarity threshold**, following `tests/test_indexer.py::test_m201_related_text_embeds_nearer_than_unrelated_text`. A threshold would freeze one checkpoint's calibration rather than the repository's claim, and would fail on ordinary model variation instead of on a broken integration.

## 13. Determinism evidence

**Claim A — semantic / query determinism. Made, and specified.** Same corpus, same embeddings, same index configuration, same query vector → **equal ordered results**, across two independently built indexes in two directories, sharing no state. This is `docs/DOCUMENT_CONTRACT.md` §8.8 item 1's definition of determinism — *repeated construction yields equal values* — applied to retrieval. `test_m201c_the_same_query_over_the_same_corpus_returns_the_same_order`.

**Claim A, metadata identity.** The persisted metadata after a rebuild describes the same index as the one held in memory, signal for signal, read from the file rather than from the object. `test_m201c_metadata_identity_survives_a_rebuild`. M2.01B's byte-identity claim for `index_metadata.json` is unaffected and still holds.

**Claim B — byte identity of the FAISS binary. NOT claimed, and NOT specified.** This is stated explicitly because the sprint brief asks for it: **no byte-identity claim is made for `index.faiss` by this sprint.** Third-party binary serialization is not a repository byte-identity contract, no repository authority establishes one, and M2.01B recorded the same position as its finding F-3. No specification in either file asserts it.

**No artificial determinism.** Nothing is memoized to produce these results. The two runtimes in the determinism specification each rebuild from the corpus in full. The one piece of state a runtime holds — the resolved index — is per-instance, does not outlive the object, and is not shared between specifications; a new runtime repeats discovery, validation and any rebuild in full, which every lifecycle specification relies on.

## 16. M2-02 disposition — **OPEN / PARTIAL**

### The classification

| | |
|---|---|
| **M2.01C query stage** | **COMPLETE** |
| **M2-02 VectorStore capability** | **OPEN** |
| **Remaining blocker** | **Authoritative `upsert` semantics** |

M2-02 is **not discharged**, and the register was not modified to suggest otherwise. RO-08 Decision 2 permits discharge *"only when the complete repository-defined `VectorStore` contract is satisfied"*. The Protocol has two methods; one is satisfied.

**Passing a structural test is not evidence of discharge**, and this sprint does not treat it as such: `test_m201c_no_component_satisfies_the_vector_store_protocol` asserts that neither delivered component is a `VectorStore` and that neither has an `upsert` attribute, so the OPEN state is specified rather than merely stated.

### The exact remaining contract gap

**`upsert(self, chunk_id: str, vector: list[float]) -> None`.**

Sprint M2.01B recorded as its finding F-5 that `upsert` had *"no caller and no stated semantics at 2A"*. This sprint reached the same wall from the other side and can now state the obstruction concretely, which is more than a scoping preference:

> **The frozen `upsert` signature cannot carry the inputs the repository's own index identity is computed from.**
>
> RO-08 Decision 3 binds an index's usability to eight signals. Two of them cannot be maintained under `upsert` as declared:
>
> - **`chunk_fingerprint`** is computed over the ordered `(chunk_id, chunk_text)` sequence (RO-08 Decision 1). `upsert` receives `chunk_id` and `vector` — **no chunk text.** An implementation therefore cannot recompute the fingerprint, cannot leave it correct, and cannot honestly mark it unknown, because a stale fingerprint is precisely what RO-08 Decision 1 was sought to prevent.
> - **`document_hashes`** records the Knowledge Manifest's `documents[].id` and `.hash`. `upsert` receives **no document identity**, so an upserted vector for a chunk of a new document leaves the index claiming a corpus it no longer represents.
>
> Consequently `vector_count` and `chunk_ids` would move while the fingerprint did not — and an index whose identity is partly false is worse than one that is merely stale, because compatibility validation would pass on it.

Additionally, and independently, none of the following is stated by any repository authority: accepted input shape (single vs. batch), whether an upsert of an unknown `chunk_id` appends or is an error, the ordinal-stability consequence for the position → chunk-id mapping under replacement or deletion (`IndexFlatIP` is append-addressed), whether an upsert persists immediately or defers, and whether a mutated index is still comparable to a rebuilt one.

**No semantics were invented for any of it.** `upsert` was not implemented, not stubbed, and not raised as `NotImplementedError` to manufacture structural conformance — the brief bars that, and it would have made `isinstance(..., VectorStore)` pass while the capability remained unbuilt.

### The exact authority a future ruling would need to supply

Recorded so a Repository Owner ruling has a concrete agenda rather than a restated problem. **This list is a request for authority, not a proposal, and not a ruling.**

1. **Identity under mutation** — what happens to `chunk_fingerprint` and `document_hashes` when a vector is upserted, given that `upsert` receives neither chunk text nor document identity. (Options a Repository Owner might weigh: widen what the *implementation* is handed without touching the Protocol; declare a mutated index unidentified and therefore unpersistable; or declare mutation out of scope for Milestone 2A entirely.)
2. **Input shape** — single mutation or batch; whether a batch form is a separate method or a convention.
3. **Insert vs. replace** — whether an unknown `chunk_id` appends, and whether a known one replaces in place or is an error.
4. **Ordinal stability** — whether the position → chunk-id mapping must survive mutation, given that `IndexFlatIP` addresses by append order and has no removal that preserves ordinals.
5. **Persistence** — whether an upsert writes the artifact immediately, defers to an explicit save, or leaves the persisted artifact deliberately behind the in-memory one.
6. **Staleness interaction** — whether a mutated index may pass compatibility validation at all, and against what expected identity.
7. **Rebuild relationship** — whether mutation is an optimization of rebuild (and must therefore produce an equivalent index) or a distinct lifecycle with its own guarantees.
8. **Whether M2-02 requires `upsert` at Milestone 2A at all**, given that the corpus is rebuilt whole and no repository caller mutates an index. If the answer is no, the Repository Owner would need to state how M2-02 is discharged against a two-method Protocol — which is a governance question this sprint may not answer.

**Question 8 is the shortest path to discharge**, and stating that is an engineering observation, not a recommendation about which way it should be answered.

### Register synchronization — **not performed**, and why

`docs/DEFERRED_ITEMS_REGISTER.md` was **not modified by this sprint.**

§1.3 permits an implementation sprint to synchronize the register when **both** conditions hold: *"the sprint **explicitly discharges** a registered capability, and the sprint's brief **explicitly authorizes** register synchronization."* **The first condition is not met** — M2.01C discharges nothing. The sprint brief's own instruction is conditional in the same direction: *"If M2-02 is fully satisfied, update the Deferred Items Register…"*, and it is not satisfied.

Two consequences are disclosed rather than resolved:

- **The M2-02 row now lags by one sprint.** It records M2.01B's delivered stage and describes M2.01C in the future tense — *"Sprint M2.01C establishes the remaining Protocol conformance"*. Its **status remains correct**: M2-02 is OPEN, and the row says so. What it does not yet record is that M2.01C has run, delivered `query`, and left the gap at `upsert`. **Synchronizing that is a Repository Owner action**, and this report is its evidence.
- **This diverges from the M2.01B precedent.** M2.01B edited its own M2-02 row while also discharging nothing, reporting §1.3 as met. That edit is committed and accepted, and is not reopened here (**CP-3**). This sprint took the stricter reading because the alternative — an implementation sprint editing canonical governance authority on a permission whose stated precondition it does not meet — is the more serious error of the two, and is the harder one to reverse.

`docs/ENGINEERING_TRACEABILITY_REGISTER.md` was likewise **not modified**. Its §1.2 governing test admits only retrospective rows and bars anything describing work to be scheduled; the findings below that await a Repository Owner decision are exactly that. The precedent is explicit: M2.01B did not add its own findings there — **Sprint RO-09 transcribed the one that warranted it**, later. This sprint follows that precedent and records its findings here.

## 17. Engineering findings

Only findings supported by repository evidence. None is a ruling, and none allocates a capability.

**F-1 — `upsert`'s frozen signature cannot maintain the index identity RO-08 Decision 3 defines.**
The specific, evidence-backed form of M2.01B's F-5. `upsert(chunk_id, vector)` carries neither chunk text nor document identity, so it cannot maintain `chunk_fingerprint` or `document_hashes`. This is the blocker holding M2-02 OPEN, and §16 records the authority a ruling would need to supply. **No implementation is attempted, and none should be until the ruling exists.**

**F-2 — the BGE query prefix remains an open, unauthorized decision.**
`sample_rag/embedding.py` records that BGE's asymmetric retrieval prefix (*"Represent this sentence for searching relevant passages:"*) *"belongs to the **query** side of a retrieval system"* and that **M2-02** / **M2-04** own the question. This is the sprint that owns the query side, and it **did not apply one**: no repository authority establishes a prefix, applying it would change what every query vector *is* relative to every stored vector, and RO-08 and RO-09 authorize no such decision. `test_m201c_no_query_prefix_or_transformation_is_applied` specifies the current behaviour so that adopting a prefix later is a deliberate, visible decision. **Non-blocking:** semantic retrieval demonstrably works without it (§12). Whether the published checkpoint's asymmetric usage should be adopted is a Repository Owner decision, and `docs/DEFERRED_ITEMS_REGISTER.md` **M2-15** (*embedding benchmarking; retrieval-quality optimization*) is where a comparison would belong.

**F-3 — tie-break among exactly equal similarities is unspecified.**
FAISS does not specify its ordering among equal scores, and no repository authority states a tie-break for the vector route — unlike the lexical route, where `sample_rag/retriever.py` anchors ties to canonical rank and then committed corpus position. It cannot arise from distinct stored vectors under exact flat search, so nothing is owed today. It would become a real question the moment a second route's results are fused with these (**M2-04**). **Observation only.**

**F-4 — the semantic route has no production caller.**
M2.01B's F-6 recorded that the artifact was *"validated but not yet consumed"*. It is now consumed by `VectorIndexRuntime`, which is itself constructed only by specifications: `sample_rag/retriever.py` still ranks lexically, and no CLI or script path builds a runtime. **This is correct for this stage and was a deliberate boundary.** Routing `Retriever.retrieve` to the vector route requires choosing a retrieval-route label, a score semantics for the frozen `RetrievalResult` contract, and a rule for combining two routes — which *is* **M2-04** hybrid retrieval, and which the sprint brief bars. The seam is ready; wiring it is the next capability's work, not this one's.

**F-5 — the runtime directory sits beside a module of the same stem.**
`sample_rag/vector_index/` (derived state) and `sample_rag/vector_index.py` (source) share a name in one package directory. Python resolves the module, because a directory without `__init__.py` is a namespace package and namespace packages rank below modules in the import system's finder order; verified empirically on Python 3.12.3. **Not a defect, and no implementation is owed** — but the two are distinguished only by an ignore rule's trailing separator, which §6.2 specifies for that reason. A future sprint choosing to rename either should treat it as a deliberate decision rather than a tidy-up.

**F-6 — full-suite timing on this environment varies by ~2×.**
The same 468-specification baseline measured 88.43 s and 183.10 s in one session with no repository change between them (§14). Embedding throughput on WSL2 is not stable enough for an absolute suite time to be a repository fact. The **increment** attributable to a sprint remains meaningful and is what §14 reports. **Observation only; no test-architecture change was made, and none is proposed.**
