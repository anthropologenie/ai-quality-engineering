## 3. Work Packages 2 & 3 — Canonical metadata and manifest regeneration

### 3.1 How canonical status is decided

`CANONICAL_SOURCES` in `scripts/build_manifest.py` — an **explicit declaration** of canonical source paths, not a rule that infers approval from a filename.

**Why declared rather than derived.** `docs/MILESTONE_1A.md` build item 1 states: *"Filenames remain the authoritative source of document versioning; the manifest intentionally does not duplicate that metadata."* Parsing `v2_2`/`v2_3` to decide approval would have this module infer a **corpus-composition decision** from a version string. Approval and version are different properties — a corpus with no version suffixes at all would still need one document designated canonical — and `docs/P3.7.3_…` §3.4 reserves the designation to the Repository Owner. A declaration records the decision; a heuristic would manufacture one.

`is_canonical(source)` is a total function of the normalized source path — no filesystem access, no ordering dependence — so designation is reproducible for any corpus, and an undesignated corpus yields "nothing is canonical" rather than a guess.

## 4. Work Package 4 — Deterministic retriever update

### 4.1 The precedence chain

`Retriever.rank_candidates` sort key moved from `(-overlap, position)` to `(-overlap, canonical_rank, position)`:

```text
Equal retrieval score  →  Canonical document  →  Committed corpus order
```

`_canonical_rank` returns `0` for a canonical document's chunk and `1` otherwise. It is a **sort rank, never a score**: it is not added to, combined with, or compared against any retrieval score, and it is read only after the score comparison has already tied. `canonical_document_ids` defaults to the empty set, so an omitted designation reproduces pre-sprint ordering exactly.

### 4.2 Evidence that scoring did not change

Measured for the manual-review question, before and after:

| | Before | After |
|---|---|---|
| Result `score` | `0.285714` | **`0.285714`** |
| Retrieval route | `LEXICAL` | **`LEXICAL`** |
| `candidates_matched` | `16` | **`16`** |
| Per-chunk scores, ranks 1–5 | all `0.285714` | **all `0.285714`** |

**Every one of the five retrieved chunks carries an identical score in both runs.** The candidate set is the same size, the score distribution is the same, and only the order within a score tie differs — which is precisely the boundary Work Package 4 draws. No chunk was boosted, no chunk was excluded, and no chunk whose score differed from another's changed places with it.

The `diagnostics` key set was deliberately left unchanged, so that no downstream difference could be attributed to a new field rather than to canonical selection.

### 6.3 Why the last two were not met — a conflict inside the brief

**These two expectations are not reachable by a tie-break, and Work Package 4 permits only a tie-break.**

Sixteen candidates tie at score `0.285714`. The canonical document contributes **three** of them. With `top_k = 5`, three canonical chunks fill ranks 1–3 and the remaining two slots necessarily fall to the next-ranked candidates, which are the superseded document's. Reordering cannot empty those slots — only **excluding** non-canonical documents could, and exclusion is:

- not a tie-break, since it would apply regardless of whether scores tie; and
- barred by Work Package 4: *"Canonical document identity SHALL be used ONLY after existing deterministic retrieval scoring has produced equal-scoring candidates."*

Work Package 4 states this constraint three times and closes with *"This sprint resolves document identity only. It does NOT modify retrieval scoring."* Work Package 6's final two bullets require behaviour only filtering can produce. **The implementation follows Work Package 4**, because it is the implementation directive and the more emphatically stated constraint, and because filtering would change which chunks are candidates — a retrieval-behaviour change this sprint is not authorized to make.

Recorded as finding **F-1**. Resolving it requires a Repository Owner decision, not an implementation choice — see §8.

### 7.1 The specification change, and why it was necessary

`tests/test_cli.py` enforces the CLI's orchestration structurally, asserting `called == APPROVED_CALL_SEQUENCE` as an **exact ordered list**. The CLI genuinely gained a loading step, so the list that describes it had to gain one too.

Two properties were preserved rather than relaxed:

- **The authority boundary is untouched.** `BARRED_AUTHORITY_MODULES` is unchanged and `test_the_cli_does_not_reach_the_evaluation_layers` still passes: `scripts/cli.py` imports no barred module. It reaches the Knowledge Manifest only through `scripts/run_retrieval.py` — exactly as it already reaches the Chunk Corpus through `load_corpus`, since `scripts.build_chunks` is itself a barred module reached transitively through that same seam. This follows committed precedent rather than establishing a new one.
- **The pipeline shape is unchanged.** `load_canonical_documents` sits adjacent to `load_corpus` and before any component is constructed, so the sequence remains *load everything → construct → invoke*.

The second edit — `expected_output` — was **forced by the specification catching a real divergence**: that helper builds the reference pipeline independently, and until it also loaded the designation, it disagreed with the CLI. It failed, correctly, on the first run. Recorded as finding **F-4**.

## 9. Known limitations

1. **Duplicate wording remains eligible for retrieval because canonical designation is an ordering mechanism rather than an exclusion mechanism** — reached for questions where the canonical document supplies fewer than `top_k` tying chunks (F-1). The duplicate is now *ordered after* the canonical wording rather than before it.
2. **Cross-version questions are degraded by design** (F-3). Two of 22 Evidence Trace entries are affected; one changed classification.
3. **Canonical designation is corpus-specific.** `CANONICAL_SOURCES` names one path. Milestone 1B's corpus expansion (**1B-05**, **1B-06**) will add document classes that need their own designation, and an undesignated class defaults to non-canonical.
4. **`documents[].indexed` remains unresolved** — untouched, per **1B-11**.
5. **No deduplication exists.** Two chunks with identical or near-identical text from different documents are distinct candidates. Semantic deduplication is not a Milestone 1A capability.
6. `manifest_version` remains `1.0` despite a schema extension (F-2).
