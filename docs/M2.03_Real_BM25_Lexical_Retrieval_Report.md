## 1. What this sprint did

It replaced `sample_rag/retriever.py`'s distinct-term-overlap scorer with **genuine
Okapi BM25**, at the lexical retrieval boundary that already existed, behind the
frozen `retrieve(query, filters) -> RetrievalResult` contract.

```
canonical chunks (sample_rag/chunks.json)
        │
        ├──────────────► semantic route   BGE + FAISS      → chunk ids   (M2-01 / M2-02, untouched)
        │
        └──────────────► lexical route    BM25             → chunk ids   ◄── THIS SPRINT
                                                                │
                                                     stops here │  M2-04 (RRF) is not implemented
```

**No RRF, no hybrid ranking, no score fusion, no reranking, no query rewriting or
expansion, no SQL filtering, no JobOps, no generation, no Ragas, no DeepEval.**
The two routes remain independently callable and are not connected by any code
path — §12 records how that is enforced structurally rather than asserted here.

**No new dependency.** BM25 is `math.log` and `collections.Counter`; `requirements.txt`
is unchanged. **No change to `EmbeddingProvider`, `VectorStore`, FAISS, the vector
index, `chunks.json`, or the chunk contract.** **RO-08, RO-09 and RO-10 are
untouched.**

## 4. The lexical corpus representation

`BM25Statistics`, derived once per `Retriever` in `__init__` from the texts of the
chunks it was handed:

| Field | Meaning | BM25 term |
|---|---|---|
| `document_count` | number of chunks | `N` |
| `document_frequencies` | term → number of chunks containing it | `df(t)` |
| `term_frequencies` | per-chunk `Counter` of terms | `tf(t,d)` |
| `document_lengths` | per-chunk token count | `|d|` |
| `average_document_length` | mean token count over the corpus | `avgdl` |

**Positional, and carrying no chunk id.** Index `i` describes the chunk at index `i`
of the collection — the corpus order the retriever already treats as authoritative.
The statistics object therefore introduces **no second identity for a chunk**;
`test_m203_statistics_are_positional_and_carry_no_chunk_identity` asserts the field
set exactly, so a later `chunk_id`, `bm25_id` or `lexical_id` field fails.

**Derived once, over the retriever's own copy.** They are a property of the corpus,
not of a query: deriving them per call would make every query pay for the corpus and
would let two queries against one retriever disagree about `avgdl`. Building them
over the copy `__init__` already makes means a caller mutating its list afterwards
cannot invalidate them.

## 5. The BM25 contract

### Formula

```
                                        tf(t,d) · (k1 + 1)
score(q, d) =   Σ      idf(t) · ──────────────────────────────────────
              t ∈ q             tf(t,d) + k1 · (1 − b + b · |d| / avgdl)


idf(t) = ln( 1 + (N − df(t) + 0.5) / (df(t) + 0.5) )
```

`t` ranges over the query's terms **with multiplicity**. A term absent from `d`
contributes nothing and is skipped rather than added, so an all-unknown query yields
exactly `0.0`.

### Parameters — **engineering decision, not repository authority**

| Parameter | Value | Why |
|---|---|---|
| `k1` | **1.2** | Term-frequency saturation. The conventional default of the Okapi BM25 literature (Robertson & Zaragoza, *The Probabilistic Relevance Framework*, §3.3) and of Lucene's `BM25Similarity` |
| `b` | **0.75** | Length normalization. Same two sources |

Phase 0 finding 9 established that no committed authority states either value. They
are named module constants (`BM25_K1`, `BM25_B`), reported in every runtime record
(`diagnostics["bm25_k1"]`, `diagnostics["bm25_b"]`), and accepted as parameters by
`BM25Statistics.score` — so retuning them is a visible change to a named constant,
not a rediscovery of what the code meant. **They were not tuned.** §11 explains why
tuning them here would have been the wrong sprint's work.

### IDF variant — **engineering decision**, and the load-bearing one

The **non-negative** (Lucene) IDF was chosen over the classic
`ln((N − df + 0.5) / (df + 0.5))`. The reason is a repository invariant, not taste.

The classic form goes **negative** for any term carried by more than about half the
corpus. On a 259-chunk corpus drawn from one resume that is routine, not
pathological, and a *matching* chunk could then score below zero. Two committed
behaviours depend on that not happening:

- `EMPTY_RESULT_SCORE` is `0.0`, and `docs/MILESTONE_1A.md` Architectural AC2
  requires `score` to be *meaningful* on both the match and no-match paths. A
  negative score for a match would collide with the no-match value's meaning.
- The CLI's abstention path is reached by **lexical disjointness**
  (`docs/P3.6.0_CLI_Integration_Report.md` §9.6). *Matched* and *scored above zero*
  must remain the same statement.

With this form every `idf` is **strictly positive**, so neither behaviour can be
reached by arithmetic accident.
`test_m203_inverse_document_frequency_is_strictly_positive_for_every_corpus_term`
asserts it over a whole vocabulary, together with the monotonicity that shows the
positive floor was not bought at the cost of the weighting.

### Degenerate cases, defined rather than left to arithmetic

| Case | Behaviour |
|---|---|
| `df(t) = 0` (unseen term) | Heaviest weight the corpus can express — never a division by zero — but `tf = 0` in every document, so it never contributes |
| `avgdl = 0` (corpus holds no term) | The length ratio is taken as `0.0`. Unreachable through `rank_candidates`, which has no document to score; defined so `score` is total for a direct caller |
| `N = 1` | `idf = ln(1 + 0.5/1.5) > 0`, and `avgdl = |d|` so the ratio is exactly 1. The classic IDF form would have given `ln(0.5/1.5) < 0` here |
| Chunk tokenizing to nothing | `tf = 0` for every term, so never a candidate — but its zero length still lowers `avgdl`, correctly: it is a document that carries no term |

## 6. Tokenization and normalization

**Inherited unchanged from Sprint P3.3.1** — `tokenize(text)` is
`re.compile(r"[a-z0-9]+").findall(text.lower())`, and the *same function* is applied
to corpus chunks and to queries, so no term can exist in one and not the other.
Preserving it rather than authoring a BM25-specific tokenizer is what keeps the
repository with one lexical preprocessing rule instead of two.

Every decision the BM25 contract had to make, stated because BM25 weights precisely
what this function emits — a silent change to any row would change every `tf`, every
`df` and every document length in the corpus:

| Aspect | Behaviour | Example |
|---|---|---|
| **Case** | Folded to lowercase before matching | `Python` ≡ `python` |
| **Punctuation** | Every non-`[a-z0-9]` character is a separator, discarded | `CI/CD` → `ci`, `cd`; `end-to-end` → `end`, `to`, `end` |
| **Whitespace** | Separator; runs collapse | `"  a \t\n b  "` → `a`, `b` |
| **Empty tokens** | Not representable — the pattern needs ≥1 character | `"..."` → `[]` |
| **Repeated terms** | Preserved, in reading order. This is what supplies `tf` and `|d|` | `alpha alpha beta` → three tokens |
| **Numeric terms** | Kept, weighted like any other term. No parsing, rounding or units | `led 15 engineers` → `led`, `15`, `engineers` |
| **Mixed alphanumerics** | One term | `alpha2beta` → one token |

**Deliberately absent, and the absence is the contract:** no stemming, no
lemmatization, no stop-word removal, no synonym or acronym expansion, no fuzzy or
edit-distance matching, no spelling correction, no query rewriting. No repository
authority requires any of them; each would make the match set depend on a linguistic
resource this repository does not carry; and query rewriting and expansion are
explicitly out of this sprint's scope.
`test_m203_no_stemming_lemmatization_or_stop_word_removal_is_applied` asserts the
absence directly, and
`test_m203_the_tokenization_contract_is_exactly_as_documented` covers the ten rows
above as named cases.

### Query-term handling — **engineering decision**

**Multiplicity counts.** `score` iterates the query's terms rather than its term set,
so `"alpha alpha"` weights `alpha` twice. That is the formulation of the reference
implementations (Lucene, `rank_bm25`), and dropping it would silently make
`"python python"` identical to `"python"`.

**Summation runs over `sorted(query_terms)`**, not the caller's word order. Floating-
point addition is not associative, so without a canonical order two spellings of the
same query could differ in the last bits, round differently, and rank differently —
determinism that holds per-query but not across equivalent queries. Ordering a
query's terms changes nothing about which documents match, so nothing is lost.
`test_m203_query_word_order_does_not_change_any_score` asserts it.

## 7. Deterministic ranking and tie-breaking

**All three ordering levels are Sprint P3.3.1's and P3.7.5's, unchanged.** This
sprint replaced only what the first level compares. **No new tie-breaker was
invented, and no second chunk identity was introduced to break one.**

| Level | Key | Origin |
|---|---|---|
| 1 | BM25 score, **descending** | This sprint replaced the overlap count here |
| 2 | Canonical document ahead of superseded (`0` / `1`) | Sprint P3.7.5, unchanged |
| 3 | Committed corpus position, **ascending** | Sprint P3.3.1, unchanged |

**Level 2 remains a sort rank, not a weight.** It is read only after level 1 has tied,
is never added to or compared against a score, and cannot promote a lower-scoring
chunk. `test_m203_the_canonical_tie_break_is_preserved_and_still_sits_between`
asserts both halves.

**Level 3 makes the order total.** Two chunks cannot share a corpus position, so the
sort key is injective over the candidate set and the surviving order cannot depend on
Python's sort implementation.
`test_m203_the_ordering_is_total_over_the_committed_corpus` asserts injectivity over
the committed corpus rather than asserting a sequence.

**Ranking is on the rounded score** — `round(score, 6)`, `BM25_SCORE_PRECISION`. An
engineering decision, for two reasons, both about determinism rather than
presentation: the ranked order is then explained by the very numbers
`diagnostics["scores"]` records, and the tie-break becomes a reachable, testable path
rather than a theoretical one that float noise would hide. Exact ties do occur on
this corpus — duplicated text across resume versions produces them —
so `test_m203_equal_scores_are_broken_by_committed_corpus_position` exercises a real
case, not a hypothetical one.

**Determinism is specified, not observed.** Six specifications enforce it:
repeated-query identity over ten calls on one retriever *and* against a freshly
constructed one (whole diagnostic record compared, not just the ids); word-order
invariance; total ordering; the statistics being derived once; and the tokenizer
being a total function of its input with no locale, clock or environment
participating.

## 8. Contract-visible changes

The four `RetrievalResult` fields, the route label, and all 15 pre-existing
`diagnostics` keys survive. What changed inside them:

| Change | From | To | Why |
|---|---|---|---|
| `score`, `diagnostics["scores"]` | overlap ÷ distinct query terms, in `[0, 1]` | **BM25 score**, unbounded | A BM25 score is not a fraction of anything. Dividing by query length would produce a number that looks like a proportion and is not one — and any *scheme* for making two routes' scores comparable is **score fusion**, which is **M2-04**'s and not this sprint's |
| `diagnostics["query_terms"]` | sorted distinct set | sorted bag, **with multiplicity** | It is the exact input to the score the same record reports, and under BM25 a repeated query term is part of that input. No consumer read this key |
| `diagnostics["stub"]` | `True` | **`False`** (`LEXICAL_STUB`) | See below |
| `diagnostics` | 15 keys | **18 keys** — adds `bm25_k1`, `bm25_b`, `average_document_length` | With `corpus_size` and `scores` already present, the record now carries everything needed to recompute any score in it. `diagnostics` is the contract's own **open mapping**, which is where `docs/MILESTONE_1A.md` build item 4 puts per-query runtime detail |
| `Retriever.rank_candidates(query_terms)` | `set` | sequence | An implementation detail of P3.3.1, not part of the frozen contract; no caller outside the module |
| `Retriever.statistics` | — | new read-only property | A score is explainable only against the corpus statistics that produced it |
| `score_chunk` | overlap scorer | **removed** | It computed the behaviour this sprint replaced, and had no caller outside the module. Verified by repository-wide search |

### On `diagnostics["stub"]` — **engineering decision, with an in-repository precedent**

`docs/MILESTONE_1A.md` build item 4 froze the marker so that placeholder values could
be asserted *"on structure **and** semantics now"*, and states the intent explicitly:

> Milestone 2 swaps values inside an already-correct shape rather than changing the
> shape itself.

Sprint M2.03 is that swap for the lexical route. The precedent is
`Indexer.index(...).stub`, which **Sprint M2.01A flipped `True → False`** for
**M2-01** on exactly this reasoning — recorded in
`tests/test_indexer.py::test_1b03_the_index_declares_what_kind_of_vectors_it_holds`:

> a marker that could only ever say `True` would have stopped being one the moment a
> real provider existed.

Leaving it `True` would have made every runtime record assert something false. **No
existing specification asserted the retrieval marker's value** — verified by
repository-wide search; `tests/test_generator.py`'s `REQUIRED_DIAGNOSTICS` and
`GENERATION_STUB` govern *generation* diagnostics, which are untouched and still
`True` until **M2-06**. `sample_rag/generator.py`'s comment was updated for exactly
that reason: it claimed to *mirror* the retrieval marker, and now explains why the
two no longer share a value.

### On the route label — **deliberately unchanged**

`retrieval_route` and `diagnostics["retrieval_method"]` still read **`LEXICAL`**, not
`BM25`. `LEXICAL` names the *route* in the approved Hybrid Retrieval architecture —
*Structured (SQL) + Lexical (BM25) + Semantic (Vector) → RRF* (`docs/roadmap.md`
§1.1) — and BM25 is the ranking function that route now uses, not a fourth route.
Renaming it is also not free: `docs/roadmap.md` §2.3 sketches an *expected route*
vocabulary of `BM25 / Vector / SQL / Hybrid`, and
`datasets/golden/resume_evidence_trace.json` carries
`expected_retrieval_route: null` on all 22 entries with `scripts/build_evidence_trace.py`
**enforcing** the null (route inference is deferred to Milestone 2 by its Decision A).
Whether the observed route label and that planned expectation vocabulary should
converge is retrieval-*evaluation* work over a dataset this sprint may not touch, not
lexical-scoring work. Renaming is therefore left undone rather than done unilaterally.
`diagnostics["sql_filter_applied"]` continues to report the unexercised structured
branch separately.

**The lexical/semantic distinction is made explicit, not implied.**
`test_m203_bm25_carries_no_semantic_understanding` presents a query that is a
faithful paraphrase of a chunk — *supervised personnel* for *led a team of
engineers* — asserts the two are token-disjoint, and asserts the route retrieves
**nothing**. That is recorded as a property, not a caveat: the repository's reason for
keeping a *separate* semantic route is exactly this gap, and **M2-04** is where the
two are combined. No specification in the module asserts that a higher BM25 score
means a better answer.

Four of the new specifications were themselves wrong on first run and were corrected
against the implementation, not the reverse:

- a saturation test that varied document length while varying `tf`, confounding the
  two effects — rewritten over three equal-length documents so it isolates `k1`;
- a paraphrase that shared the stop-words *a* and *of* with its chunk — replaced, and
  the disjointness now asserted rather than assumed;
- an import allowlist that had not accounted for `generator.py`'s architecture-approved
  dependency on the `RetrievalResult` contract (`docs/architecture.md` §5,
  `Generator → Retriever`);
- a "BM25 lives in one module" check written as a substring search over source text,
  which this sprint's own comment synchronization in `sample_rag/generator.py` then
  tripped — rewritten over *declared names*, which is what it meant.

Recorded because the corrections are visible in the module's docstrings as reasoning,
and a reader should know which way each correction ran. The last one is worth naming
in particular: a specification that fails on a comment is testing the wrong thing, and
it failed for that reason rather than because a boundary was crossed.

## 15. Findings

### F-1 — BM25 length normalization interacts badly with header-sized chunks

**Observed.** Retrieval quality against the 22 Evidence Trace expectations fell on
every measure (§11).

**Diagnosed, with evidence.** The mechanism is the chunk-length profile of this
corpus meeting BM25's length normalization:

| Measurement | Value |
|---|---|
| Corpus chunk length (tokens) | min 1, median 15, mean 17.20, p90 34, max 106 |
| Chunks of ≤ 3 tokens | **48 of 259** — section headers and the name line, emitted as their own chunks by the structure-aware chunker |
| Expected-evidence chunk length | mean **37.59**, median 28 — well above the corpus mean |
| Mean length of chunks the overlap scorer retrieved | 53.63 (11 of 108 were ≤ 3 tokens) |
| Mean length of chunks BM25 retrieves | **17.32** (**51 of 108** are ≤ 3 tokens) |

A worked case, for the question *"How many years of experience does Karthik have?"*:
BM25's top five are three copies of `KARTHIK S R` (3 tokens) and two of
`PROFESSIONAL EXPERIENCE` (2 tokens). The expected evidence is a 40-token body chunk
beginning *"Quality Engineering leader with around 7.5 years…"*. The headers win
because `|d| / avgdl ≈ 0.17` makes their length penalty almost nil, and one
moderately rare matched term at almost no penalty beats three common terms at full
penalty.

Confirmed by a sensitivity sweep over `b` alone, holding the implementation fixed —
**diagnostic evidence, not a proposal, and not applied**:

| `b` | Hit rate | Precision@K micro | Recall@K micro |
|---|---|---|---|
| 0.00 | 0.6364 | 0.1296 | 0.3784 |
| 0.25 | 0.5000 | 0.1019 | 0.2973 |
| 0.50 | 0.5000 | 0.1019 | 0.2973 |
| **0.75** *(shipped)* | **0.4091** | **0.0833** | **0.2432** |
| 1.00 | 0.4091 | 0.0833 | 0.2432 |

Monotone in `b`, which identifies length normalization as the dominant mechanism.
Note that even at `b = 0` BM25 scores below the overlap scorer's 0.7273 — the
remainder is IDF rewarding one rare term over several common ones, on a corpus where
the expected evidence tends to be the chunk that matches *more* of the query.

**Why this sprint did not chase it.** Three reasons, in order of weight:

1. **It would be tuning the runtime against the repository's own 22 benchmark
   questions.** Selecting `b` by which value scores best on the Evidence Trace would
   make the retriever a function of the benchmark. The repository already reasons
   this way one component over: `docs/GENERATION_CONTRACT.md` §18 bars the Generator
   from reading the benchmark authorities because *"a Generator that reads any of
   them can answer those 22 questions and nothing else, while appearing to work."*
   That is a boundary on *reading*, not on tuning, so it is cited as the analogous
   principle rather than as a rule this sprint would have broken — but fitting `b`
   to the same 22 questions arrives at the same place by a different route.
2. **It is another capability's work.** `k1`/`b` selection is retrieval-quality
   optimization — register **M2-15**, placed at Milestone 2C precisely because it
   *"require[s] a retrieval-quality signal to optimize against"*, and that signal is
   Ragas (**M2-07**). Chunk-size revision is **M2-17**. Both are out of this
   sprint's scope by name.
3. **The gap is partly what the semantic route is for.** Several of the newly-missed
   questions are paraphrases; BM25 cannot reach them by construction (§10's
   `bm25_carries_no_semantic_understanding`). Recovering them is **M2-04**'s fusion,
   not a lexical-tuning problem.

**Disposition sought.** None is established here, which is why §14 proposes the
register row rather than writing it. The Repository Owner's choice is between
allocating the `b`/`k1` question to **M2-15**, the chunk-granularity question to
**M2-17**, treating the shortfall as expected until **M2-04** fuses the routes, or
some combination.

**What this finding is not.** It is not a defect in the BM25 implementation. The
formula, the statistics, the ordering and the determinism are all specified and
verified independently of any quality metric.

### F-2 — A stale figure was found, not caused, in `tests/test_retrieval_metrics.py`

That module's docstring cited *"the corpus scores 0.1308 micro precision"* as a fact
about the P3.3.1 scorer. The overlap scorer measures **0.1481** against the corpus as
committed today. The figure was measured against Milestone 1A's two-document,
172-chunk corpus and drifted when the Milestone 1B Corpus Synchronization changed the
corpus underneath it — **before this sprint, and for an unrelated reason**. It was
never an assertion, only prose.

Synchronized by removing the quoted number rather than replacing it: a dated
measurement belongs in a report, not in a test module where it reads as a
specification. The docstring now points at §11 of this report and at
`python -m scripts.evaluate_retrieval`. No assertion changed.

### No authority discrepancy was found

Nothing in this sprint required a new Repository Owner ruling, and none is created.
No committed authority contradicts another on the lexical route, on BM25, on chunk
identity or on the ranking contract. §14's two register entries are **proposals for
review**, not rulings and not edits.
