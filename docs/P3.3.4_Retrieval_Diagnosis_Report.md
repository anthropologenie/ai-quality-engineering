## 2. Diagnosis Method

### How ALTM rules were applied

Each evaluated question carries two pieces of committed evidence: its Retrieval Evaluation record (classification, expected/observed/matched chunk sets and counts) and its Retrieval Metrics row (`chunk_recall_at_k`, `chunk_precision_at_k`). The engine matches that evidence against the symptom column of `docs/altm.md` §5 and applies the **first matching row in the document's own order**:

| Evidence | §5 row applied |
|---|---|
| `recall == 0` | ALTM-RETRIEVE-2 — "Missing answer despite evidence existing in the corpus" |
| `0 < recall < 1` | ALTM-RETRIEVE-3 — "Low recall on a known-answerable query" |
| `recall == 1` and `precision < 1` | ALTM-RETRIEVE-4 — "Low precision on a known-answerable query" |
| `recall == 1` and `precision == 1` | none — §5 is a lookup from an observed symptom; absent one, no row applies and no diagnosis is emitted |

Row order is the tie-break, and it is a property of the document rather than of the implementation: a zero-recall question is trivially also a low-precision question, and `docs/altm.md` §5 lists "Low recall" before "Low precision" while §7's workflow asks whether retrieval *found* the correct evidence before asking anything about noise. `docs/altm.md` §10 Principle 1 — one failure has one primary origin — is why exactly one row is applied rather than every row that matches.

The premise of ALTM-RETRIEVE-2 is verified, not assumed: Sprint P3.3.2 validated referential integrity, so every expected chunk id exists in the committed Chunk Corpus. The row's symptom — *evidence existing in the corpus* — holds in full.

**No diagnostic rule was created.** Every symptom, stage, component, metric and investigation string carried on a diagnosis is copied verbatim from a §5 row, and a specification (`test_every_rule_symptom_appears_verbatim_in_altm`) reads `docs/altm.md` and asserts it.

### Documented metric vs. available evidence

§5's detection metrics for these rows are **Context Precision** and **Context Recall** — Ragas metrics reserved for Milestone 2 and computed nowhere in this repository. Each diagnosis therefore carries both: `documented_metric` (the rule's own text, verbatim) and the deterministic Milestone 1A measurements actually available (`chunk_recall_at_k`, `chunk_precision_at_k`). The two are deliberately not conflated, and no Ragas metric is claimed or computed.

### Derived rule-ID mapping (Work Package 3)

Scheme: `ALTM-<STAGE>-<n>`, where `<STAGE>` is the row's **first-listed** Likely Stage and `<n>` numbers rows within that stage in §5's top-to-bottom order. Both halves are properties of the document, so a row added to §5 later appends an identifier rather than renumbering existing ones. `docs/altm.md` was not modified.

| rule_id | §5 Observed Symptom (verbatim) | Likely Stage (verbatim) | Reachable? |
|---|---|---|---|
| `ALTM-INFER-1` | Hallucinated fact not in any source document | Infer | No |
| `ALTM-KNOWLEDGE-1` | Answer cites the wrong document version | Knowledge | Yes — never fired |
| `ALTM-RETRIEVE-1` | Right topic, wrong specific document retrieved | Retrieve | Yes — never fired |
| `ALTM-RETRIEVE-2` | Missing answer despite evidence existing in the corpus | Retrieve or Assemble | Yes → Retrieve |
| `ALTM-INDEX-1` | Contradictory answer across repeated runs on the same input | Index or Infer | Yes → Index — never fired |
| `ALTM-KNOWLEDGE-2` | Stale answer despite a recent source update | Knowledge | Yes — never fired |
| `ALTM-RETRIEVE-3` | Low recall on a known-answerable query | Retrieve | Yes |
| `ALTM-RETRIEVE-4` | Low precision on a known-answerable query | Retrieve | Yes |
| `ALTM-INFER-2` | False confidence on an unanswerable question | Infer or Final Answer | No |
| `ALTM-ASSEMBLE-1` | Correct evidence retrieved, answer still wrong | Assemble or Infer | No |
| `ALTM-POST-PROCESS-1` | Answer correct pre-guardrail, wrong as delivered | Post-Process | No |
| `ALTM-EVALUATE-1` | Regression after a prompt or corpus change, previously passing | Evaluate | No |
| `ALTM-FINAL-ANSWER-1` | Faithful, grounded, but doesn't answer the actual question | Final Answer | No |

13 identifiers for 13 rows. A rule naming only unreachable stages resolves to no stage and raises rather than silently acquiring one.

### Stage reachability (Work Package 5)

Assemble, Infer, Post-Process, Evaluate and Final Answer have no implemented component in this repository — `docs/architecture.md` §5 marks Generation a stub and §9 places generation in Milestone 2. A two-stage §5 row is resolved by dropping the unreachable stage: "Retrieve or Assemble" becomes **Retrieve** because there is no Context Builder to fail. That is a consequence of what is implemented, not a re-reading of the rule — the other stage is excluded because the component does not exist, not on evidence.

## 5. Root-Cause Summary

Descriptive only. No fix, improvement, or corrective action is proposed anywhere below.

**Every diagnosis localizes to the Retrieve stage.** No Knowledge-stage or Index-stage diagnosis was produced for any question.

**Recurring pattern 1 — recall is bimodal.** 10 questions retrieved every expected chunk (`recall == 1`); 8 retrieved none (`recall == 0`); only 4 fall between. Retrieval either finds the expected evidence completely or misses it entirely, with a narrow middle.

**Recurring pattern 2 — precision is uniformly capped.** Every diagnosed question with any relevant evidence scores `precision == 0.2`; the 8 zero-recall questions score `0.0`. No question exceeds 0.2. `top_k` is fixed at 5 while 21 of 22 questions expect fewer than 5 chunks (`expected_count` distribution `{1: 15, 2: 4, 4: 2, 5: 1}`), so `ALTM-RETRIEVE-4` fires for every question that achieves full recall.

**Recurring pattern 3 — confidence is fully determined by recall.** On this evaluation the confidence value is a deterministic function of `chunk_recall_at_k` alone, and therefore carries no information beyond the Sprint P3.3.2 classification it mirrors (Complete ↔ Full Coverage, Partial ↔ Partial Match, Insufficient ↔ No Match). This is a consequence of the evidence available, not of the assessment rule.

**Dominant repository finding — the Knowledge stage cannot be diagnosed at all.** Both Knowledge-stage rules turn on *which document version* was returned, and their documented detection is a freshness check against the source. Retrieval Evaluation records carry chunk identity only, with no document identity — the same limitation Sprint P3.3.3 recorded when deferring Document Recall. Under the frozen dependency rule the Knowledge stage is therefore unreachable **in practice** even though it is reachable **in principle**, and 8 of 22 questions are recorded as Insufficient Evidence precisely because a Knowledge-stage explanation cannot be excluded.

### Independence of the two derivations (Work Package 8)

The validator does not read the engine's diagnoses to produce one — they are an argument to `compare()` alone, after every independent diagnosis already exists. Independence is structural on three axes:

1. **No import of `evaluation.retrieval_diagnosis`** — not its rule selection, confidence assessment, constants, or record shape. Enforced by an AST allowlist specification.
2. **A different derivation path** — the engine reads `chunk_recall_at_k` and `chunk_precision_at_k` from the metrics report; the validator recomputes both from the records' chunk id sets and uses its own values, consulting the metrics report only to confirm the two agree.
3. **A different rule-selection shape** — the engine returns early from an ordered chain; the validator enumerates every §5 row whose symptom the evidence exhibits and takes the first in document order, so the ordering itself is independently verified.

**One deliberate exception:** both import `evaluation/altm_rules.py`. That module is a transcription of `docs/altm.md` §5, not engine logic — it is the *authority*, and WP8 asks the two implementations to apply the same documented rules. Two separate transcriptions would test whether they were copied identically rather than whether the rules were applied consistently.

## 7. Implementation Observations

Observations only. No repository improvement is recommended.

1. **The sprint's own worked example is not derivable.** WP5 gives `Observed: Resume v2.2 retrieved / Expected: Resume v2.3 → Knowledge → Freshness rule`. That diagnosis requires document identity, which Retrieval Evaluation records do not carry and which the frozen dependency rule bars the engine from obtaining. Zero Knowledge-stage diagnoses were produced. This is the same architectural limitation recorded in the P3.3.3 report when Document Recall was deferred, now reaching the diagnosis layer.

2. **Sprint P3.3.2's aggregate summary does carry document distributions** (`expected_document_distribution`, `observed_document_distribution`), derived at a layer permitted to read the Chunk Corpus. They are not part of the *records* the dependency rule admits, so the Diagnosis Engine cannot consume them.

3. **The v2.2/v2.3 document-dominance pattern recorded in P3.3.1 and P3.3.2 is neither confirmed nor refuted here.** It is the specific alternative that keeps 8 questions at Insufficient Evidence: `ALTM-KNOWLEDGE-2` cannot be excluded, and it also cannot be asserted.

4. **`ALTM-KNOWLEDGE-1`, `ALTM-KNOWLEDGE-2`, `ALTM-RETRIEVE-1` and `ALTM-INDEX-1` are reachable in principle and fired zero times.** All four require evidence no permitted input carries: document version for the Knowledge rows, document identity for `ALTM-RETRIEVE-1` ("Right topic, wrong specific document retrieved"), and cross-run comparison for `ALTM-INDEX-1` ("Contradictory answer across repeated runs") — which the repository's determinism guarantees make vacuous by construction.

5. **Confidence adds no information beyond classification on this evaluation.** Complete ↔ Full Coverage, Partial ↔ Partial Match, Insufficient ↔ No Match, exactly. A future evidence source that distinguishes upstream causes would break that correspondence.

6. **Diagnosis is emitted only for questions exhibiting a symptom.** All 22 exhibit one here (Exact Match count is zero), so the "without symptom" path is exercised by specification rather than by the corpus.

7. **`ALTM-RETRIEVE-4` fires for every full-recall question** because `top_k` is fixed at 5 while 21 of 22 questions expect fewer than 5 chunks. The rule's documented investigation — *"Check for near-duplicate or loosely-related chunks crowding results"* — is recorded on each diagnosis and was not performed; performing it is outside this sprint.
