## 1. Why the sprint stopped

Sprint M2.01B was briefed as a contract-first implementation sprint targeting register capability **M2-02 — Vector store implementation**, using FAISS under the election recorded at `docs/DEFERRED_ITEMS_REGISTER.md` §6 (Sprint RO-06 / RO-07).

Its brief carried explicit STOP rules, two of which fired:

- *Phase 1* — *"If the existing abstraction does not provide enough authority to define the required persistent contract safely: STOP. Do not silently expand repository authority."*
- *Phase 3, NO SILENT HASHING CONTRACT* — *"If safe stale-index detection requires creating a NEW canonical corpus/chunk identity or fingerprint that is not already defined by repository authority: STOP. Do not silently establish a new repository identity convention."*

The sprint halted during Phase 0 / Phase 1 re-anchoring, before any implementation, dependency installation or file modification. **`faiss-cpu` availability was not a factor** — version 1.15.0 publishes for this platform (linux/aarch64). All three blockers were authority blockers.

## 2. Discrepancy 1 — Missing canonical chunk-content identity for persisted-index freshness

### 2.1 Repository facts

| Identity | Source at `28cf3d5` | What it actually covers |
|---|---|---|
| Document id | `scripts/build_manifest.py:92-94` — `sha256(source)[:12]` | The normalized **source path**, not content |
| Document content hash | `documents[].hash` — SHA-256 of the source file | **Source-file bytes** |
| Chunk id | `sample_rag/chunker.py:141-145` — `sha256(f"{document_id}:{chunk_index}")[:16]` | **Position**, explicitly not content |
| Chunk-content / corpus fingerprint | *Did not exist* | — |

Three primary citations establish that the absence was a decision rather than an omission:

- `sample_rag/chunker.py:142-143` — *"Deterministic chunk id, derived from position — (document_id, chunk_index) — **not from chunk content** (Chunk Contract §10, §14.1)."*
- `docs/CHUNK_SERIALIZATION_PLAN.md:306` — *"No collection-level metadata beyond version + list | **ADR-0001 §2** | No `document_count`, **`corpus_hash`**, or timestamp field | Container stays minimal."* The chunk serialization deliberately remained minimal, and **ADR-0001 §2 did not authorize corpus-level metadata in the chunk container.**
- `docs/DATA_QUALITY_VALIDATION_PLAN.md:482` — `documents[].hash` *"covers source **bytes**, not extracted text… it detects **source** drift, never **extraction-mechanism** drift."*

**Consequence:** chunk text could change while every existing identity signal remained unchanged.

### 2.2 Why this mattered

A persisted vector index could become stale when chunk content changes through chunking or extraction behaviour — a chunker configuration or strategy change, or a change in the extraction mechanism — **even if the document hash, the chunk ids and the chunk count all remain unchanged.** Embeddings are computed from chunk *text*, so such an index would validate as fresh and be silently wrong.

The repository already documents this exact blind spot for DQ-1, which is bounded to source-byte drift by the same limitation.

### 2.3 Authority boundary

The M2.01B brief explicitly prohibited silently inventing a new canonical identity. Detecting the drift above required precisely such an identity, so the sprint could not proceed without a ruling.

### 2.4 Resolution — RO-08 Decision 1

RO-08 authorized an **index-local fingerprint** over the ordered `(chunk_id, chunk_text)` sequence used to construct a persisted vector index.

Recorded explicitly, as RO-08 states:

- it **lives in the persisted vector-index metadata**
- it **does not modify `sample_rag/chunks.json`**
- it **does not redefine chunk ids**
- it **does not amend ADR-0001**
- it is **not a new canonical corpus identity** — it is an index-local identity mechanism
- the exact **algorithm, canonical serialization and input construction remain an M2.01B engineering choice**, to be selected from the nearest existing repository identity/hash conventions, and **must be recorded in that sprint's engineering evidence**

## 3. Discrepancy 2 — M2-02 persistence-only implementation conflicted with the existing VectorStore Protocol completion contract

### 3.1 Repository facts

| Authority at `28cf3d5` | Content |
|---|---|
| `docs/architecture.md` §5 | `VectorStore` responsibilities: *"**Persist and query** vector representations"*; Interface column: `VectorStore.upsert(...)`, `VectorStore.query(...)` |
| `docs/architecture.md` §7 | The frozen Protocol, including `query(self, vector: list[float], top_k: int) -> list[str]` |
| `sample_rag/vector_store.py:49` | Preserves **both** `upsert` and `query`, unchanged |
| `tests/test_indexer.py:263` | `test_1b02_a_partial_store_does_not_satisfy_the_protocol` — a store carrying `upsert` alone is asserted **not** to be a `VectorStore` |

### 3.2 The contradiction

Sprint M2.01B was intentionally bounded to persistence/foundation work and **prohibited query and retrieval implementation** — `query()`, `search()`, similarity search, nearest-neighbour retrieval and top-k were all on its MUST NOT list, and its Phase 10 required confirming that none had been implemented.

But the repository's own specification defines `VectorStore` conformance as **both** methods. **M2.01B therefore could not honestly discharge M2-02 while remaining persistence-only.** A persistence-only component is, by `test_1b02_a_partial_store_does_not_satisfy_the_protocol`, not a `VectorStore`.

A second, related gap was recorded at the same time: **`docs/architecture.md` defines no persistence lifecycle for the seam.** "Persist" appears as a *responsibility* in §5, but no `save`, `load`, `open` or metadata method exists anywhere in repository authority, so the persistence contract's shape could not be derived from the architecture as the brief's Phase 1 required.

### 3.3 Resolution — RO-08 Decision 2

RO-08 keeps **M2-02 as ONE capability** and stages its acceptance:

| Sprint | Establishes | M2-02 |
|---|---|---|
| **M2.01B** | Persistent FAISS foundation, persistence, loading, identity, source/chunk mapping, compatibility validation, freshness validation and deterministic rebuild semantics | **Remains OPEN** — shall not be discharged |
| **M2.01C** | Remaining `VectorStore` Protocol conformance, including `query(vector, top_k) -> list[str]` | Dischargeable once the complete contract is satisfied |

**No `M2-02a` or `M2-02b` capability was created**, no row was duplicated, and the `VectorStore` Protocol itself was not altered — RO-08 permits staged implementation of an existing contract, nothing more.

## 4. Discrepancy 3 — Existing FAISS freshness authority depended on unavailable JobOps/timestamp semantics

### 4.1 Repository facts

- `docs/architecture.md:264` describes FAISS freshness in exactly one place: *"FAISS `VectorStore` implementation, with **content-hash + last-indexed-timestamp** freshness tracking **against JobOps SQLite**."*
- **JobOps integration is not available in Milestone 2A.** The 2A corpus is resume-only.
- **JobOps-related capabilities were reallocated to Milestone 2B under RO-06** — registers **1B-05**, **1B-06**, **1B-07**, **1B-12**.
- **`created_at` was previously excluded from deterministic artifact design** — `docs/MILESTONE_1A.md:102-103`, *Contract Change — `created_at` removed*: a creation timestamp *"would make the manifest non-deterministic for an identical corpus generated at two different times — in direct conflict with the deterministic artifact contract."*
- **`documents[].indexed` was removed by R-02** — `docs/MILESTONE_1A.md:107-108`, ruling **R-02 — Runtime Index Semantics**, Sprint 1B.2B: indexing state is runtime state; the manifest is a deterministic knowledge artifact.
- **Timestamp-based manifest identity was therefore not available** as a Milestone 2A freshness mechanism.

### 4.2 The contradiction

The only committed description of FAISS freshness is composed of two elements the repository could not supply at Milestone 2A: a corpus that is not connected until 2B, and a timestamp the repository has twice deliberately declined to persist. **M2.01B could not safely implement the broader JobOps/timestamp freshness design against the resume-only corpus without inventing new repository authority.**

### 4.3 Resolution — RO-08 Decision 3

RO-08 authorizes a bounded Milestone 2A freshness basis:

- document content hash
- ordered chunk-id set
- chunk count
- index-local chunk-content fingerprint
- embedding model identity
- embedding model revision
- embedding dimension
- relevant FAISS index configuration / type

**Timestamp-based and JobOps freshness remain deferred to Milestone 2B.** RO-08 records this as a scoped execution rule for the resume-only Milestone 2A implementation; `docs/architecture.md` §9's broader JobOps-oriented freshness design is neither deleted nor redesigned.
