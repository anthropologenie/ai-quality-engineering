## 2. Evaluation Algorithm

### Comparison algorithm

For each Evidence Trace entry, in Evidence Trace order:

1. Load expected chunk ids from `expected_chunk` (Evidence Trace Dataset — the Retrieval Expectation Authority).
2. Load observed chunk ids from `RetrievalResult.diagnostics["retrieved_chunk_ids"]`.
3. Convert both to sets and classify.

Pairing is required to be total and one-to-one in both directions. An entry with no `RetrievalResult`, a `RetrievalResult` with no entry, and a repeated entry id are each refused with `RetrievalEvaluationError` rather than summarized — none is a retrieval finding, and classifying an unobserved entry as No Match would report that retrieval found no evidence when retrieval was never executed.

### Set-based evaluation

Comparison uses **set semantics**, per the Work Package 2 Repository Decision. `expected_chunk` is ordered ascending by `chunk_index` (Sprint P3.2.4 Decision G); `retrieved_chunk_ids` is ordered by retrieval ranking (Sprint P3.3.1). These orderings are intentionally different, and comparing them positionally would report a disagreement neither authority asserts. **Membership** is what is evaluated. Ranking is out of scope and belongs to P3.3.3.

Every chunk-id collection on an evaluation record is a **sorted list**, sorted by chunk id — not by rank and not by `chunk_index`. Identity is the only ordering both input authorities agree on, and sorting by it keeps no field's order dependent on set iteration.

### Classification rules

With `E` = expected chunk id set and `O` = observed chunk id set:

| Category | Condition | Meaning |
|---|---|---|
| Exact Match | `O == E` | Exactly the expected chunks; none missing, none additional. |
| Full Coverage | `E ⊂ O` | All expected chunks retrieved, alongside non-expected chunks. |
| Partial Match | `E ∩ O ≠ ∅` and `E ⊄ O` | Some expected evidence retrieved, some missing. |
| No Match | `E ∩ O = ∅` | No expected evidence retrieved. Observed retrieval may be empty or entirely unrelated. |

No separate "Unexpected Match" category exists; zero-overlap behaviour is represented entirely by No Match.

### Domain restriction discovered during implementation

The four conditions are mutually exclusive **except at `E = ∅`**, where `O == E` (Exact Match) and `E ∩ O = ∅` (No Match) are simultaneously true for empty observed retrieval. This was surfaced by the exhaustive mutual-exclusivity specification, not reasoned about in advance.

`E = ∅` is unreachable from the Retrieval Expectation Authority: `scripts/build_evidence_trace.py` refuses to derive an entry resolving to zero chunks, and `validate_evidence_trace` rejects an empty `expected_chunk` on read. Rather than resolve the ambiguity by predicate ordering — which would have made the classification an artifact of evaluation order — the engine **enforces the domain**: `evaluate_entry` raises `RetrievalEvaluationError` on an empty expectation. The four categories therefore partition every pair the repository can produce, exactly. Empty *observed* retrieval remains reachable and is No Match.

Notes on how each check is performed:

- **Determinism** — `evaluate` is called twice on identical inputs and the results compared. It reads no clock, no environment and no filesystem, and holds no state between calls.
- **Stable ordering** — two orderings, both required: evaluation records follow Evidence Trace order exactly, and every id list within a record is sorted.
- **Referential integrity** — every expected *and* observed chunk id is checked against the committed Chunk Corpus's id set.
- **Exhaustive classification** — the four conditions are **re-derived** from each record's own id lists rather than read back off the stored `classification`. Reading the label back would be tautological: `classify` returns exactly one value by construction, which proves nothing about whether the conditions partition the space.
- **Classification totals** — the four category counts must sum to the question count.
- **Repository integrity** — SHA-256 digests of all five authorities, compared across a full evaluation.

## 5. Implementation Observations

Observations only. No cause is proposed and no fix is suggested.

### For P3.3.3 — Retrieval Metrics

1. **Zero Exact Match at HEAD.** `top_k = 5` is fixed while `expected_count` ranges from 1 to 5; 18 of 22 entries expect fewer than 5 chunks. Exact Match is structurally unavailable to those entries under the current `top_k`.
2. **Per-question overlap and corpus-level overlap differ.** Distinct chunks that are expected somewhere and observed somewhere number 9; per-question matched references number 14. A chunk expected by one question and retrieved for a different one contributes to the first figure and not the second. A metrics layer must state which of the two it aggregates.
3. **Counts are carried on every evaluation record.** `expected_count`, `observed_count` and `matched_count` are materialized alongside the id lists so P3.3.3 aggregates them rather than recomputing set arithmetic at each call site.
4. **Coverage ratios already exist and share a denominator.** `expected_chunk_utilization` and `observed_chunk_utilization` are rounded to four places, matching `scripts/run_retrieval.py`'s `corpus_utilization`, so the P3.3.1 and P3.3.2 coverage figures are directly comparable. Neither places expected and observed on opposite sides of the division; neither is a retrieval metric.
5. **Ranking is fully preserved but unread.** `scripts/evaluate_retrieval.py` carries `retrieved_chunk_ids` in ranking order, and `RetrievalResult.diagnostics` retains `scores`, `ranking` and `matched_terms`. Every input a ranking-sensitive metric needs is present and untouched.

### For P3.3.4 — Retrieval Diagnosis

6. **Observed document distribution is systematically dominated by Resume v2.2.** The Chunk Corpus is exactly balanced — 86 chunks per document — and the expectation authority points almost entirely at v2.3 (34 of 36 expected references). Observed retrieval inverts this: 76 of 107 observed references are v2.2 chunks. The rank-1 chunk is a v2.2 chunk for 21 of 22 questions, and 3 questions retrieved v2.2 chunks exclusively.

   **Cross-reference — P3.3.1.** This is the same document-distribution pattern P3.3.1 recorded. That sprint's runtime observation reported `unique_documents_retrieved = 2` and `document_coverage = 1.0` — retrieval spanning both catalogued documents rather than the one the Golden Dataset was regenerated from (commit `64a3e16`, *"regenerate Golden Dataset from canonical Resume v2.3"*; commit `39ed0e4`, *"promote Resume v2.3 as canonical knowledge source"*). P3.3.1 established the observation at runtime level, without expectation; P3.3.2 records the same pattern with the expectation authority in view. `docs/AI_Quality_Metrics_Reference.md` §Layer 1 already carries the corresponding Knowledge-layer Freshness row.

   *Note:* Sprint P3.3.1 left no committed report document — its runtime and the observation above exist in `scripts/run_retrieval.py` (`summarize`, `document_coverage`), which is untracked at HEAD. This cross-reference points at that artifact and its docstring.

7. **Two expected references point at v2.2.** `meta_qa_resume_f026_reasoning_01` and `meta_qa_resume_f026_reasoning_02` expect chunks from `3f3797c1134c`. The expectation authority is therefore not exclusively v2.3.
8. **Non-expected retrieval is not judged.** `unexpected_chunk_ids` is recorded on every evaluation record but carries no verdict: the Evidence Trace Dataset asserts which chunks carry the answer, never that no other chunk may be retrieved alongside them. 29 distinct chunks were observed and never expected.
9. **One question retrieved fewer than `top_k`.** `meta_qa_resume_f008_lexical_01` observed 2 chunks. No question produced empty retrieval.

No explanation, cause, or remedy for any of the above is offered here. Diagnosis belongs exclusively to P3.3.4.
