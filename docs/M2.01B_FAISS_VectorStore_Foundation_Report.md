## 3. VectorStore contract discovered, and why the component is separate

`docs/architecture.md` §5 gives `VectorStore` the responsibility *"Persist and query vector representations"* but its Interface column names only `upsert(...)` and `query(...)`. **No persistence lifecycle — no `save`, `load`, `open` or metadata method — exists anywhere in repository authority.** Persistence is a stated responsibility with no stated interface.

Implementing the Protocol would require `query`, which this sprint forbids and RO-08 Decision 2 assigns to M2.01C. So the FAISS-backed component lives in a **new module, `sample_rag/vector_index.py`**, and `sample_rag/vector_store.py` is untouched — which also keeps `test_1b02_no_vector_store_implementation_is_shipped` (asserting that file declares the Protocol *and nothing else*) passing unmodified.

The component is deliberately **not** a `VectorStore`, and `test_m201b_the_vector_store_protocol_is_not_implemented_here` asserts exactly that. RO-08 Decision 2 records this non-conformance as the authorized staged state.

## 4. Minimum M2.01B contract

```
chunk_fingerprint(chunks) -> str                       # RO-08 Decision 1

@dataclass(frozen=True)
VectorIndexIdentity(model_id, model_revision, dimension, index_type, metric,
                    vector_count, chunk_ids, chunk_fingerprint, document_hashes)
    .mismatches(other) -> list[str]                    # report, not bool

identity_for(index, chunks, documents, embedding_provider) -> VectorIndexIdentity

class FaissVectorIndex
    .build(index, chunks, documents, embedding_provider) -> FaissVectorIndex
    .save(directory) -> None
    .load(directory) -> FaissVectorIndex                # classmethod
    .identity -> VectorIndexIdentity
    .vector_count -> int
    .chunk_id_at(position) -> str                       # vector → chunk mapping
    .reconstruct(position) -> list[float]               # stored vector by ordinal
    .validate(expected) -> None                         # raises on mismatch

VectorIndexPersistenceError(Exception)
VectorIndexCompatibilityError(Exception)
```

## 5. Persisted artifact structure

One directory, two files:

| File | Contains | Owned by |
|---|---|---|
| `index.faiss` | FAISS's own serialization of the `IndexFlatIP` index | FAISS's format, not this repository's |
| `index_metadata.json` | `schema_version`, `index_type`, `metric`, `embedding{model_id, model_revision, dimension}`, `vector_count`, `chunk_fingerprint`, `chunk_ids[]`, `documents[{id, hash}]` | This repository's canonical JSON |

**Why two files and not one.** They are different kinds of thing. Merging would either embed a binary blob inside JSON or hide repository identity inside a third-party container this repository does not own the format of.

**How they relate.** FAISS addresses vectors by ordinal position; `chunk_ids[i]` is the chunk whose vector sits at position *i*. That ordered list **is** the vector → source/chunk mapping, and `chunk_id_at(position)` is its accessor.

**Where stored.** `VECTOR_INDEX_ROOT` (`sample_rag/vector_index/`) names the default location. **No artifact is committed by this sprint** — every specification writes to `tmp_path`. See finding **F-2**.

**How consistency is validated on load.** Both files must exist; then FAISS's own `ntotal` must equal the metadata's `vector_count`, FAISS's `d` must equal the recorded `dimension`, and `len(chunk_ids)` must equal `vector_count`. A disagreeing pair would let position → chunk-id mapping point at the wrong chunk, so it is rejected as `VectorIndexPersistenceError` — a corruption fact, not an incompatibility fact.

## 7. Dependency and FAISS configuration

| | |
|---|---|
| Package | **`faiss-cpu`** — never `faiss-gpu`, no CUDA-specific dependency |
| Exact version installed | **1.15.0** |
| Wheel | `faiss_cpu-1.15.0-cp310-abi3-manylinux_2_27_aarch64…whl` |
| Declaration | `requirements.txt`, unpinned — the file's existing convention (no entry carries a version) |
| CPU confirmation | `dir(faiss)` exposes no `Gpu*` symbol |
| Index type | **`IndexFlatIP`** |
| Metric | Inner product |

**Why `IndexFlatIP`.** Flat, exact and **untrained**: no clustering, quantization, sampling or random initialization, so two builds over identical vectors hold identical contents. An IVF or HNSW index could not offer that without a trained, seed-dependent structure — it would trade the repository's determinism discipline for a speed property no current capability needs. Inner product is chosen because M2.01A's provider returns unit-norm vectors, for which inner product *is* cosine. **Selecting a metric is an index-construction property, not a retrieval act:** nothing in this module searches or ranks.

**Reproducibility implications.** Both the index type and the metric are identity-relevant and participate in compatibility validation (CASE G), so a future change to either invalidates existing artifacts rather than silently reusing them.

## 8. Corpus, chunk and index identity

### 8.1 The RO-08 Decision 1 fingerprint — recorded exactly, as the ruling requires

| | |
|---|---|
| **Input construction** | The ordered sequence of `(chunk["id"], chunk["text"])` pairs, in the order the chunk collection is given |
| **Serialization** | `json.dumps(pairs, ensure_ascii=False, separators=(",", ":"))`, UTF-8 encoded |
| **Algorithm** | SHA-256, **full 64-character hex digest**, untruncated |

**Why JSON rather than a joined string.** JSON's escaping makes the encoding **injective**. A naive `f"{id}:{text}"` join collapses `("a", "b")` and `("a:b", "")` onto one digest; `test_m201b_the_fingerprint_framing_cannot_be_imitated_by_chunk_text` is the specification behind that choice. Compact separators because a digest input is never read by a person; `ensure_ascii=False` so the bytes hashed are the text's own UTF-8.

**Why SHA-256 untruncated.** SHA-256 is the repository's only content-hash function (`compute_sha256`, `generate_document_id`, `generate_chunk_id`). Truncation in this repository marks an *identifier* (12 and 16 characters); `documents[].hash` — the existing **content** hash, which this is the analogue of — is stored full-width.

**This is an implementation choice, not repository authority.** RO-08 authorizes the concept and its scope only, and explicitly declines to make the algorithm authority.

### 8.2 The identity signal set — exactly RO-08 Decision 3, and nothing else

| Signal | Source | Compatibility purpose |
|---|---|---|
| `document_hashes` | `documents[].id` + `.hash`, sorted by id | The corpus changed |
| `chunk_ids` | Ordered, from the chunk collection | The chunk set or its order changed |
| `vector_count` | `len(chunks)` | The chunk count changed |
| `chunk_fingerprint` | §8.1 | Chunk **content** changed |
| `model_id` | `getattr(provider, "model_id")` — `BAAI/bge-small-en-v1.5` | A different model produced these vectors |
| `model_revision` | `getattr(provider, "revision")` — `5c38ec7c405ec4b44b94cc5a9bb96e735b38267a` | Same model, different checkpoint |
| `dimension` | `Index.dimension` — 384 | The vectors are not this index's width |
| `index_type` / `metric` | `IndexFlatIP` / inner product | FAISS configuration changed |

**Vector count over the committed corpus: 259, at 384 dimensions.**

**No timestamp of any kind is recorded, and none may be.** `test_m201b_the_metadata_records_no_timestamp_of_any_kind` asserts over the serialized text that `created_at`, `indexed`, `timestamp`, `last_indexed` and `generated_at` appear nowhere. No JobOps coupling exists.

### 8.3 Compatibility and stale-index rules

An index is usable for given inputs when **every** signal above matches the identity those inputs produce; `validate()` raises `VectorIndexCompatibilityError` naming **all** differing signals, ordered corpus-level → configuration-level. Build and validation derive identity through the same `identity_for`, so the two cannot drift apart.

## 11. Determinism

**Claim A — semantic/index determinism. Made, and specified.** Identical chunks, vectors, model identity and configuration produce an equal `VectorIndexIdentity`, an equal vector count, and bytewise-equal vectors read back by ordinal (`test_m201b_rebuilding_from_identical_inputs_is_semantically_deterministic`). `IndexFlatIP` supports this structurally: exact, untrained, no randomness.

**Claim A, extended to the file this repository owns.** `index_metadata.json` is byte-identical across rebuilds, because it is serialized with the repository's own fixed `json.dumps(..., indent=2) + "\n"` call. Specified.

**Claim B — byte identity of the FAISS binary. NOT made, and NOT specified.** Third-party binary serialization is not a repository byte-identity contract and no repository authority establishes one. *Observed* during this sprint: the FAISS binary did in fact reproduce byte-identically across two builds on this environment — but that is a measurement, not a contract, and **no specification asserts it**. Recorded as finding **F-3**.

## 15. Engineering findings

**F-1 — `Index` carries no model identity, so identity must be supplied at build time.**
`Index` holds `vectors`, `dimension` and `stub`; nothing records which model produced the vectors. `build` therefore takes the provider alongside the Index and reads `model_id` / `revision` from it defensively via `getattr`, the pattern `sample_rag/indexer.py` already uses for `dimension` and `placeholder` — so the frozen `EmbeddingProvider` Protocol did not have to grow a field. A consequence worth stating: a caller that passes a provider *different from the one that built the Index* would record a false identity. Nothing in this sprint's scope can prevent that, and no repository authority couples an Index to its provider.

**F-2 — no vector-index artifact is committed, and `.gitignore` was not touched.**
`VECTOR_INDEX_ROOT` names where an artifact would be written; every specification writes to a temporary directory instead. Committing a ~400 KB FAISS binary whose byte identity the repository deliberately does not guarantee (§11) is a repository-artifact-policy decision, not a persistence one, and nothing in M2.01B or RO-08 requires it. If a committed artifact is wanted, `.gitignore` and the artifact policy `docs/CHUNK_SERIALIZATION_PLAN.md` §P7 records for `chunks.json` are where that decision belongs.

**F-3 — the FAISS binary reproduced byte-identically, but this is not claimed.**
Two builds over identical inputs produced identical `index.faiss` bytes on this environment. It is recorded as an observation only; §11 explains why no specification asserts it, and a FAISS version change or a different platform could alter it without any repository fact having changed.

**F-4 — `numpy` entered `sample_rag/` for the first time.**
FAISS's Python API takes vectors as a `numpy` array, so the persistence module imports it. It is not an embedding, vector-store or evaluation library, so A-5 is unaffected; it is admitted explicitly by the module's AST allowlist rather than tacitly. Note it was already an installed transitive dependency of `sentence-transformers`, but is now a direct import and is not separately declared in `requirements.txt` — consistent with the file's existing practice of declaring only top-level packages.

**F-5 — `upsert` remains unimplemented alongside `query`.**
The `VectorStore` Protocol has two methods and this sprint implements neither. `upsert` was left out because this artifact is built whole from a chunk corpus and rebuilt when that corpus changes; incremental mutation has no caller and no stated semantics at 2A. M2.01C, which completes the Protocol, will need both.

**F-6 — the artifact is validated but not yet consumed.**
Nothing in the runtime reads a persisted index: `sample_rag/retriever.py` still ranks lexically and no CLI path constructs one. That is correct for this stage — consumption is retrieval — but it means the artifact's real integration pressure arrives at M2.01C.
