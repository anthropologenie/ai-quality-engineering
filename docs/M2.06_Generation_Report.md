## 2. Provider

### 2.1 Selected mechanism

**ENGINEERING DECISION.** The provider is reached through the **Python standard library** — `urllib.request` and `json` — from a single module, `sample_rag/deepseek.py`.

**FACT. The third A-5 dependency exception was authorized by RO-13 and was NOT taken.** `requirements.txt` is byte-identical to its committed state. The repository remains a **two-exception** repository: `sentence-transformers` (M2.01A) and `faiss-cpu` (M2.01B).

**Why.** RO-13 authorized the category and left the selection to M2-06 after repository inspection. The inspection found:

- no HTTP client, LLM SDK or provider abstraction anywhere in the repository;
- `docs/architecture.md` §10 records *"minimal dependencies"* as a binding architectural decision;
- the repository has already refused a dependency for arithmetic it can state itself — `tests/test_lexical_bm25.py::test_m203_no_bm25_dependency_was_added` enforces that for BM25;
- the two exceptions that *were* taken were taken because the **algorithm** was the dependency (a transformer checkpoint, an ANN index), which is not the case for an HTTP POST carrying a JSON document.

Selecting an SDK would have added a dependency tree to perform a request this repository can state in full, and would have put the request and response shapes behind someone else's abstraction at precisely the boundary RO-13 asked to be kept narrow. **The exception remains available to a later sprint; it was simply not needed.** `tests/test_model_generator.py::test_m206_no_dependency_was_added` makes taking it silently a visible failure.

### 2.2 Module boundary

**ENGINEERING DECISION.** Two modules rather than one, which is the **smaller** boundary RO-13's *"one generation/provider module or the smallest equivalent boundary"* permits:

| Module | Role |
|---|---|
| `sample_rag/deepseek.py` | The provider boundary. The **only** module in `sample_rag/` that imports a network primitive |
| `sample_rag/model_generator.py` | The Generation Contract component. Imports no network primitive, opens no socket, holds no endpoint, reads no credential |

**Why.** §24.3 states that the G-14 permission is *"for one call — not a category of access."* Splitting the modules makes *"the Generator cannot reach the network except through the one sanctioned call"* a **structural property of the package**, checkable by AST, rather than a promise about a function body. `test_m206_the_generator_performs_no_io_of_its_own` and `test_m206_the_provider_boundary_is_the_only_networked_module` assert both halves, the second by glob over `sample_rag/*.py` so a module added later is covered.

### 2.3 Authoritative provider contract source

**FACT.** The endpoint, authentication scheme, request schema, response schema, documented error status codes and model identifiers were read from **DeepSeek's published API documentation at `api-docs.deepseek.com`** during this sprint — specifically its API overview, its create-chat-completion reference, its error-codes page and its model/pricing page. **None was inferred from memory.** No URL recorded here carries a credential or a query parameter of any kind.

**FACT.** The contract established:

| | |
|---|---|
| Method and URL | `POST https://api.deepseek.com/chat/completions` |
| Headers | `Content-Type: application/json`, `Authorization: Bearer <key>` |
| Response path | `choices[0].message.content` |
| Documented statuses | 400, 401, 402, 422, 429, 500, 503 |
| Published models | `deepseek-v4-flash`, `deepseek-v4-pro` |

### 2.4 Selected model

**ENGINEERING DECISION.** `deepseek-v4-flash`.

Both published models share a 1M-token context window and a 384K maximum output, so this is not a capability choice. `flash` is the smaller of the two, and M2-06 answers a single grounded question over an assembled context of a few hundred characters (measured at 611 and 323 characters in the two acceptance runs below). **No claim is made about which model produces better answers** — that is an evaluation question and evaluation is M2-07 / M2-08.

### 2.5 Request construction

**FACT.** The request body carries exactly five documented fields:

```text
model         the selected model identifier
messages      two messages: a system instruction, and a user message
stream        False — one complete JSON document, not an SSE stream
temperature   0
thinking      {"type": "disabled"}
```

No `tools`, `tool_choice`, `response_format`, `stop`, `logprobs`, `top_logprobs`, `user_id` or `max_tokens`. Tool calling and model routing are barred outright by §24.3's G-14 transition; the rest would be request-shaping decisions no authority asked for.

**ENGINEERING DECISION — `temperature: 0`.** A grounded question over supplied evidence is an extraction task, and the provider's default of 1 is tuned for open generation. **This is explicitly not a determinism claim.** §24.3 records that RO-13 *"establishes no such guarantee"* about provider-side deterministic sampling and that *"no sprint may claim one from repeated calls alone"*. The value is chosen for task fit; `answer_text` remains outside structural determinism regardless of it.

**ENGINEERING DECISION — `thinking: {"type": "disabled"}`.** The provider enables thinking by default and returns its trace as a separate `reasoning_content` field. This implementation maps `content` and nothing else, and §24.4 authorizes no new `GenerationResult` field, so the trace has nowhere to go. Leaving it enabled would spend latency and output budget producing a value the contract has no field for.

**ENGINEERING DECISION — the system instruction.** A single fixed sentence asking the model to answer from the supplied context alone and to say so when it cannot. **This is not prompt engineering and not an optimized prompt** — prompt and retrieval optimization is **M2-15** and is out of scope. It is the smallest instruction that makes the call a question *about the assembled context* rather than an open question, which is the difference between a RAG request and a chat request.

**FACT.** Request construction is deterministic. `build_request_body` is a pure function of its arguments; the same messages produce a byte-identical request document.

**FACT.** Exactly two repository values leave the repository: `prompt.context` and `prompt.query`. **No chunk id, document id, character offset, retrieval score, RRF rank, corpus path, manifest digest or repository identity is transmitted.** `test_m206_no_provenance_field_is_transmitted_to_the_provider` and `test_m206_no_repository_internal_detail_is_transmitted` assert this over the serialized request.

### 2.6 Response handling

**FACT.** `parse_completion` reads exactly `choices[0].message.content` and requires it to be a non-empty string. Every departure from the documented shape raises `ProviderResponseError`; there is no default, no fallback field and no empty-string substitution. `reasoning_content`, `usage`, `logprobs`, `system_fingerprint` and `tool_calls` are deliberately not read.

## 4. Failure semantics

**FACT.** Five conditions are distinguished, each by its own named exception, and **none is representable as a successful `GenerationResult`**:

| Condition | Raised | Class |
|---|---|---|
| `DEEPSEEK_API_KEY` absent or blank | `ProviderConfigurationError` | Configuration |
| Documented HTTP status (400/401/402/422/429/500/503) | `ProviderRequestError` | Provider |
| Undocumented HTTP status | `ProviderRequestError` | Provider |
| Timeout, DNS failure, transport failure | `ProviderRequestError` | Provider |
| Response body is not JSON | `ProviderResponseError` | Malformed response |
| Response is JSON of the wrong shape, or `content` is absent/empty/non-string | `ProviderResponseError` | Malformed response |
| `Prompt` violates §24.4 (ids and provenance disagree, offsets do not span the context, non-positive span) | `GenerationInputError` | Context assembly, observed at the generation seam |
| Valid response | — | `GenerationResult` with `outcome == "Answer"` |

**FACT.** Configuration failure and provider failure are kept distinct because they are fixed by different people: a missing credential is the operator's, a 503 is the provider's. Collapsing them would make an unconfigured repository look like an unavailable provider.

**FACT.** `GenerationInputError` is not a `ProviderError` and `ProviderError` is not a `GenerationInputError`; neither inherits from the other. Retrieval failures are unchanged and remain retrieval's own.

**FACT.** Error classification is a lookup in a fixed status→reason table, not a heuristic over provider prose — §24.3 requires error classification to remain deterministic, and a classifier that parsed the response body would vary with the provider's wording.

**FACT.** A malformed `Prompt` is rejected **before** any provider interaction, so no sanctioned call is ever spent on an artifact that could not have been constructed.

**FACT.** No retry, backoff, circuit breaker, connection pool or cache exists. One `generate` performs at most one provider call, and `test_m206_exactly_one_provider_interaction_is_performed` counts it. A retry loop would turn one sanctioned interaction into an unbounded number of them.

## 6. Supporting evidence

### 6.1 How `Prompt` provenance becomes `SupportingEvidence`

**FACT.** One `GeneratedStatement` per assembled chunk, each carrying exactly the one `SupportingEvidence` that chunk contributed:

```text
canonical chunk -> ContextBuilder -> Prompt.context + Prompt.provenance
                -> ModelGenerator -> SupportingEvidence
```

`chunk_id`, `document_id`, `character_start` and `character_end` are copied from the provenance record unchanged. `text` is recovered from `Prompt.context` by offset arithmetic: block *i*'s length is `character_end - character_start`, because `docs/CHUNK_CONTRACT.md` §17 invariant 3 freezes `text == document_text[character_start:character_end]` for every chunk.

**ENGINEERING DECISION — offset arithmetic rather than splitting on `CONTEXT_SEPARATOR`.** Splitting would have been shorter and is **wrong on any chunk whose own text contains a blank line**; `sample_rag/context_builder.py` documents its assembly as reversible only over a corpus where none does. A consumer that inherited that condition would silently mis-attribute evidence the day the corpus stopped meeting it. Offsets carry no such condition, and `test_m206_evidence_text_is_recovered_by_offset_not_by_splitting` states the difference on a corpus that breaks the naive approach. The arithmetic is checked, not trusted: a `Prompt` whose provenance and context disagree raises rather than slicing from the wrong place.

**FACT.** The evidence is constructed **before** the provider is called, and nothing in it passes through the provider. G-6's *"the Generator never constructs a chunk id"* holds under v2.0.0 exactly as under v1.0.0, and the model cannot influence any identifier in the result.

### 6.2 The G-7 boundary, stated exactly

**FINDING — F-1. The provider offers no evidence-selection mechanism, and none was invented.**

DeepSeek's chat-completion contract carries **no citation or evidence-attribution field**: no part of the response identifies which supplied span a sentence came from. Splitting the answer into claims and attributing each to a chunk would therefore have been this sprint *inventing* an attribution the provider never made — and an invented citation is worse than none, because it is checkable-looking.

The mapping implemented is therefore the smallest one the existing contract admits, and it fabricates nothing. What the artifact asserts is exactly: **these spans were assembled, and this answer was produced with them present.**

**It does not assert that the answer uses the evidence, is entailed by it, or contains nothing beyond it.**

**FINDING — F-2. An interpretive tension inside §24, resolved by applying the more specific clause.**

§24.3 states that *"§8's field definitions"* are unchanged, while §8.1 describes `answer_text` on the Answer path as *"assembled from the `statements` below and contain[ing] no content not present in them"*. The same §24.3 states, specifically and by name, that under v2.0.0 `answer_text` **"MAY be synthesized by the model"** and that *"the quotation-only derivation requirement no longer applies to it."*

The specific clause was applied: §8.1's sentence is the descriptive restatement of G-7, §16 is where guarantees are normative, and §24.3 names G-7 as one of the four that transition. `GeneratedStatement.text` remains a verbatim quotation of its own span, so the surviving half of G-7 holds unchanged.

**This is recorded as a finding, not resolved as governance.** No contract text was edited. If the Repository Owner reads §24.3's *"§8's field definitions unchanged"* as also freezing that sentence, the implementation is affected only in how it is described, not in what it does.

### 6.3 What is explicitly not claimed

**FACT.** **No faithfulness, groundedness, hallucination-absence, answer-relevancy, context-precision or context-recall claim is made anywhere in this implementation or this report.** The presence of evidence metadata is not evidence of any of them. §24.3 keeps three things distinct — structural evidence provenance, model answer synthesis, and empirical faithfulness — and records the third as *"later evaluation work, neither established nor claimed here."*

## 9. The finding that matters most

**FINDING — F-4. Two generator components now coexist, and RO-13 did not dispose of the first one.**

**The facts.**

- RO-13 authorized `Generator.generate(prompt: Prompt) -> GenerationResult` and the register's M2-06 row describes M2-06 as *"replac[ing] the quotation Generator"*.
- §24.1 states that v1.0.0 *"is not withdrawn, corrected, or falsified"* and *"remains the accurate, frozen record"* of the Milestone 1A quotation Generator — so **both contracts are live**, each authoritative for its own component (§24.1's own table says exactly this).
- `scripts/cli.py` is the sole consumer of the v1.0.0 signature.
- `docs/P3.7.6_Milestone_1A_Closure_and_Frozen_Baseline.md` §3.2 freezes `test_generator.py`'s 48 specifications and `test_cli.py`'s 27; §4 freezes the CLI's byte-identical answer and abstain reproducibility as Milestone 1A **acceptance evidence**; and §3 requires subsequent milestones to *"**extend** this baseline"* and *"**SHALL NOT redefine** it."*

**Why replacing in place was not available to this sprint.** A `scripts/cli.py` driving a model-backed generator would (a) place a **live provider call inside the deterministic pytest suite**, which this sprint is required to prevent, and (b) retire the frozen byte-identity acceptance evidence, which is a redefinition of the Milestone 1A baseline. **RO-13 authorized neither**, and choosing between them is a Repository Owner decision about Milestone 1A's frozen baseline, not an implementing sprint's.

**What was done instead.** `sample_rag/generator.py` is **unchanged, byte for byte**, and `sample_rag/model_generator.py` implements v2.0.0 alongside it. The v2 method contract is implemented literally — `generate(prompt: Prompt) -> GenerationResult`. **The class is named `ModelGenerator` rather than `Generator`**, because two classes named `Generator` both claiming the `docs/architecture.md` §5 row would be a worse outcome than a name that does not claim it.

**Where this belongs.** **M2-14** — which RO-13 §24.2 explicitly authorized and explicitly did **not** discharge (*"owned by M2-14, which remains a separate open capability"*) — already owns the §5 `Generator` row synchronization. The component-identity question is exactly that row's question. **This sprint reports it; it does not decide it, and it invented no ruling to decide it with.**

**M2-14 relationship.** M2-06 has produced the evidence M2-14 would need: the v2 signature exists, is implemented, and is executed end to end against a real provider. **That is not an automatic discharge of M2-14**, which remains OPEN and is not claimed here.
