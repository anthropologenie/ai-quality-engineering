  judge/provider findings

  The genuinely positive finding, and it is a real contrast with Ragas: DeepEvalBaseLLM is a plain-Python ABC. It is not typed against LangChain.
  The Ragas failure mode — "the custom-judge extension point is defined in LangChain types" (RO-17 D-2) — does not recur here.

  But four separate problems remain:

  1. openai is imported at module level on the metric path. Supplying a custom judge does not avoid it. Importing FaithfulnessMetric requires the
  OpenAI SDK installed and imported. RO-16 D-5 places further provider SDKs outside authority; RO-13 D-4's third A-5 exception is scoped to M2-06
  only and is untaken.
  2. The contract requires async a_generate. DeepSeekClient.complete(messages) -> str is synchronous. An async shim in evaluation/ would not modify
  sample_rag/deepseek.py — so this is surmountable — but the metrics also call generate_with_schema(prompt, schema=<pydantic model>), falling back
  to free-text JSON parsing (trimAndLoadJson) for non-native models. That is a materially weaker judgement seam than M2-07's closed single-token
  verdict vocabulary.
  3. DeepEvalBaseLLM.__init_subclass__ auto-instruments every subclass via deepeval.tracing.internal.observe_methods, wrapping generate/a_generate.
  Any repository judge adapter is silently wrapped in DeepEval's tracing layer at class-definition time.
  4. 4.1.8 ships its own DeepSeekModel — a second, competing DeepSeek provider integration inside the library.

  Decisively, on authority rather than mechanics: RO-16 D-3 and RO-17 D-4 both state that the DeepSeek judge authorization does not extend to M2-08.
  RO-16 D-3, verbatim: "Not authorized: DeepSeek for arbitrary evaluation frameworks, for M2-08 automatically, any other provider, any provider
  SDK, a model router, or general evaluation infrastructure."

  RO-14 D-2 remains binding — "no provider call enters the deterministic suite." DeepEval's intended local path is its pytest plugin (assert_test,
  deepeval test run), which runs live judge calls inside pytest. That shape is structurally incompatible; only the M2-07 injected-judge pattern
  satisfies the rule.

  Versions 0.20.4 – 4.1.4 — at import time, unless opted out before import:

  requests.get("https://api.ipify.org")        → machine PUBLIC IP retrieved

  and on each evaluation run, span.set_attribute("user.public_ip", anonymous_public_ip). The public IP is transmitted to third parties (New Relic,
  PostHog) despite the variable being named "anonymous". Opt-out is DEEPEVAL_TELEMETRY_OPT_OUT ("YES" in 2.x/3.x, boolean via pydantic-settings from

  Versions 4.1.5 – 4.1.8 (telemetry refactored into a package) — materially better, and evidently deliberately so. ipify, Sentry and New Relic are
  gone. What remains is a closed Event enum, a typed EventProperties dataclass, and an anonymous UUID in ~/.deepeval/.deepeval_telemetry.txt.
  telemetry/judge.py explicitly collapses any custom judge to provider="custom", model="unknown" to avoid "an unbounded-cardinality leak." Payload
  carries counts, metric class names, entrypoint, outcome, SDK/runtime version — no question, context, answer, score value, or judge reasoning.
  Still opt-out, still PostHog, still on by default.

  Confident AI upload — deepeval.confident.api (aiohttp + requests) is imported at module level by the metric path in 4.1.8, but every network call
  is gated on is_confident() → CONFIDENT_API_KEY. If a key is present, LLMApiTestCase carries:

  input, actual_output, expected_output, context, retrieval_context,
  metrics_data (score + judge reason), trace, metadata, comments
  That is the full T3 payload — question, retrieved context, reference answer, generated answer, score and judge reasoning — but only with an
  account configured.

  One further item, distinct from telemetry: import deepeval executes autoload_dotenv(), which reads .env, .env.{APP_ENV} and .env.local from the
  working directory into os.environ. The repository's credential model reads DEEPSEEK_API_KEY from the process environment at the moment of the call
  and never stores it. DeepEval's import-time env mutation is a change to credential-handling semantics — which RO-17 D-4 names as a condition that
  triggers a STOP.

  native alternative

  M2-07 established the pattern and it transfers to M2-08 with no adaptation:

  existing generation (GenerationResult.answer_text)
        ↓
  native evaluation metric  (evaluation/generation_metrics.py)
        ↓
  injected judge(prompt: str) -> str
        ↓
  ScriptedJudge / ConstantJudge / RefusingJudge in pytest   ← RO-14 D-2 satisfied
        ↓
  DeepSeekClient in scripts/evaluate_generation.py          ← live path, on demand
  All four Layer-3 metrics fall out of the same seam:

  ┌────────────────────┬────────────────────────────┬────────────────────────────────┬────────────────────────────────────────────────────┐
  │       Metric       │            Unit            │           Reference            │                 Judged proposition                 │
  ├────────────────────┼────────────────────────────┼────────────────────────────────┼────────────────────────────────────────────────────┤
  │ Faithfulness       │ one claim from answer_text │ assembled context, whole       │ is this claim entailed by the context?             │
  ├────────────────────┼────────────────────────────┼────────────────────────────────┼────────────────────────────────────────────────────┤
  │ Groundedness       │ one claim from answer_text │ assembled context, per passage │ can this claim be traced to a specific passage?    │
  ├────────────────────┼────────────────────────────┼────────────────────────────────┼────────────────────────────────────────────────────┤
  │ Hallucination Rate │ one claim                  │ assembled context              │ derived bookkeeping over the Faithfulness verdicts │
  ├────────────────────┼────────────────────────────┼────────────────────────────────┼────────────────────────────────────────────────────┤
  │ Answer Relevancy   │ one claim                  │ the question                   │ does this a what was asked?                  │
  └────────────────────┴────────────────────────────┴────────────────────────────────┴────────────────────────────────────────────────────┘

  Groundedness being strictly per-passage where Faithfulness is whole-context is precisely the distinction AI_Quality_Metrics_Reference.md insists
  on — and expressing it is a matter of which reference the prompt shows the judge, which the native seam controls and DeepEval does not expose.

  Cost: one module, one test module, zero new dependencies, zero new runtime, T0.

  recommendation

  Do not adopt DeepEval. Implement M2-08 natively.

  This is not a fit problem alone; it is a capability problem first. DeepEval does not provide Groundedness at y version in its history, so
  adopting it would mean either dropping the repository's stated strongest Layer-3 differentiator or hand-rolling it anyway — at which point the
  native path is already built and the framework is carrying openai, PostHog, an unused Confident AI client and an A-5 exception for the three
  metrics it does cover.

  Stated the way RO-17 stated it for Ragas: not adopted under the current constitution; not defective, and not permanently prohibited.

  - roadmap.md §7 / altm.md §12 — Promptfoo is a Milestone 3 capability. The repository is in Milestone 2A. Nothing authorizes it now, and nothing
  needs to.

  native alternative

  altm.md §6 is precise about what this actually is: "Not a single-stage metric — a comparison methodology applied across two full runs of every
  stage." A methodology, not a tool.

  The repository already has every input: a committed golden dataset, deterministic retrieval, the M2-18 execution evidence layer, native evaluation
  report pytest. Regression evaluation is therefore pin a baseline artifact → re-run the existing scripts/ entry points → diff the two JSON
  documents → fail on threshold regression. That is a Python module and a test module, reusing the exact evidence artifacts the repository already
  produces — and it stays deterministic, which a live-provider Promptfoo eval does not.

  What Promptfoo genuinely adds that pytest does not: a matrix runner across many providers/prompt variants, a browser result viewer, anon
  DSL, and a hosted sharing UI. All four are real. None of them is the capability ALTM Layer 4 asks for, and three of the four are outside
  repository scope entirely.

  recommendation

  Do not adopt Promptfoo. Not now, and — on this evidence — not at Milestone 3 either, unless the capability definition changes.

  The runtime boundary is grossly disproportionate to the capability: a Node ≥22 runtime, a second package ecosystem, a web server, an embedded
  database, a model router, two provider Sd a second credential boundary, in exchange for a diff of two JSON artifacts the repository already
  writes.
