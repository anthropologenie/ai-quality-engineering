# Sprint M2.12 — Context Builder / Prompt Foundation

**Register capability:** **M2-12** — *Assemble stage — Context Builder, `Prompt` artifact*.
**Starting HEAD:** `f6b2b70` (*docs(governance): record M2-04 activation and fix artifact test*).
**Working tree at start:** clean.
**Baseline suite at start:** **594 passed**.

This sprint establishes the seam between completed retrieval and future real
generation. It assembles what retrieval produced; it does not decide what
retrieval should have produced.

```
M2-04 RRF                       (sample_rag/fusion.py, unmodified)
      │
      ▼
ordered canonical chunk ids     list[str]
      │
      ▼
ContextBuilder.resolve          ◄── this sprint
      │
      ▼
ordered canonical chunk records
      │
      ▼
ContextBuilder.assemble         ◄── this sprint
      │
      ▼
Prompt                          generation-ready representation
      │
      ▼
M2-06 real generation           NOT this sprint
```

**This sprint does not deliver validated or end-to-end RAG.** It delivers a
Context/Prompt foundation. End-to-end RAG is reached only after **M2-06**
supplies a model that consumes a `Prompt`.

**ENGINEERING DECISION** (no repository authority specified the behaviour),
**FINDING** (discovered during implementation or validation), **UNRESOLVED

## 1. Contract discovery

### 1.1 `docs/GENERATION_CONTRACT.md` — the primary gate

**FACT — the contract is frozen at v1.0.0 and defines no `Prompt`.** Status:
*"Approved (Frozen)"*, Milestone 1A. It defines the `GenerationResult`
artifact, its eleven fields, thirteen invariants and fourteen guarantees. It
defines **no prompt, no prompt field, no prompt assembly, no context
representation, no separator, no label, no citation format and no context-size
or token-budget requirement.**

**FACT — the contract explicitly *refused* to define one, and recorded why.**
§6.2 (gap **G-2**) evaluated three options for the Generator's input and
rejected option (a), *"Define a `Prompt` contract in this sprint"*, because it
*"would design the Assemble stage — a different component, a different ALTM
stage, and a different contract — inside a Generation sprint."* §21 lists *"The
`Prompt` artifact, the Context Builder, and the Assemble stage"* as explicitly
out of scope, and §15 records `prompt` / `assembled_context` as fields
deliberately omitted from `GenerationResult`.

**FACT — the contract assigns the Generator no context-assembly
responsibility, and structurally prevented it acquiring one.** §6.2 rejected
option (c), *"Generator constructs its own prompt internally"*, because it
*"would silently absorb the Assemble stage into the Generator, making a future
Assemble-stage failure undiagnosable."* The approved and implemented signature
is `Generator.generate(query: str, retrieval: RetrievalResult) ->
GenerationResult` (§17, §22/G-2).

**FINDING — the critical case the sprint brief asked about does not hold.**
Context assembly is **not** substantially specified or implemented inside the
Generator. `sample_rag/generator.py` consumes `RetrievalResult` directly and
constructs one `GeneratedStatement` per retrieved chunk; its `_assemble` method
joins *statement texts into an answer*, which is Infer-stage output assembly,
not Assemble-stage prompt assembly. **No duplicate Context Builder was
therefore created, and no parallel prompt mechanism exists.**

**FACT — the contract anticipates this sprint by name.** §6.2: *"The §5
signature remains the Milestone 2 target, reached when a Context Builder
exists."*

### 1.2 Existing `Prompt` representation

**FACT — none exists.** `Prompt` is *named* by `docs/architecture.md` §5, §7
and `docs/glossary.md`, and is excluded by name from Milestone 1A by

field, a schema, a serialization or a constructor for it.** A repository-wide
search finds no `Prompt` class, dataclass, dict schema or type alias at HEAD.

### 1.3 The Context Builder's existing interface — the authority that governs this sprint

**FACT — `docs/architecture.md` §5 defines the component and its interface in
full**, and it is the authority M2-12 implements:

|---|---|---|---|---|---|
| **Context Builder** | Assemble retrieved chunks into a prompt within budget | `ContextBuilder.assemble(chunks, query) -> Prompt` | Retriever | 1A | Context-overflow handling under real token budgets |

**FACT — `docs/architecture.md` §4 defines the Assemble stage:** inputs
*"Ranked chunks, query"*, output *"Assembled prompt"*, responsibility *"Fit

**FACT — `docs/roadmap.md` §1.1 allocates M2-12 to Milestone 2A**, listed

## 2. Implementation

**Files added — two, both new. No existing file was modified.**

| File | Contents |
|---|---|
| `sample_rag/context_builder.py` | `Prompt`, `ContextBuilder`, `ContextAssemblyError`, `CONTEXT_SEPARATOR` |
| `tests/test_context_builder.py` | 45 specifications |

**FACT — the seam implemented:**

```
ContextBuilder(chunks)                              corpus-bound, as Retriever is
    .resolve(chunk_ids)   -> list[chunk record]     ordered, positional, length-preserving
    .assemble(chunks, query) -> Prompt              docs/architecture.md §5, verbatim
```

**FACT — `assemble` is implemented at `docs/architecture.md` §5's signature
exactly.** No parameter was renamed, reordered or re-typed. The repository's
governance precedent for refining a §5 interface row is a downstream
**contract** amending it explicitly (`docs/MILESTONE_1A.md` build item 4 over
the `Retriever` row — recorded as **D-6**), which is a Repository Owner action
and not an implementing sprint's. **No authority document was edited by this
sprint.**

**ENGINEERING DECISION — `resolve` is a second, separately named method.**
§5's `assemble` takes *chunks*; **M2-04** returns *ids*. Rather than
re-signature `assemble` (barred, above) or hide the lookup inside it, the
identity step is named and independently specified, so a caller composing
`assemble(resolve(fused_ids), query)` crosses the identity boundary in the
open. This is the smallest repository-consistent way to satisfy both the
frozen interface and the actual retrieval output shape.

**ENGINEERING DECISION — the corpus is bound at construction**, exactly as
`Retriever.__init__` binds it, copied into a private list for the same stated
reason: a caller's later mutation cannot change what the builder resolves
against. Corpus id uniqueness is **not** re-validated — `sample_rag/chunker.py`
already raises `ChunkConstructionError` on a duplicate id, and a second check
here would be a second owner of an invariant the Chunker holds.

**FINDING — a new abstraction was required, minimally.** `Prompt` had to be
introduced because none existed (§1.2) and the Assemble stage's output is
undefined without one. It is three fields and a frozen dataclass. **No prompt
framework, template engine, renderer, registry or strategy interface was
created**, and no general-purpose prompt abstraction exists in the repository
after this sprint.

**FINDING — nothing was extracted from the Generator, because there was
nothing to extract** (§1.1). `sample_rag/generator.py` is **byte-identical to
HEAD**.

## 3. Ordering and identity

### 3.1 Supplied RRF ordering is preserved — proof

**FACT — by construction.** `resolve` iterates the supplied sequence
positionally and appends; `assemble` joins in arrival order and derives
`chunk_ids` positionally from the same list. There is no sort, no comparison
key and no reordering operation anywhere in the module.

**FACT — verified structurally, not only by example.**
`test_m212_assembly_applies_no_sort` parses the module's AST and asserts no
call to `sorted`, no `.sort`, and no `key=` argument exists anywhere in
`sample_rag/context_builder.py`. **A module that cannot sort cannot reorder any
input**, including inputs no specification presented.

**FACT — verified behaviourally, against every competing signal.**
`test_m212_order_is_not_re_derived_from_any_ranking_signal` supplies an order
in which the first chunk is simultaneously the longest, the last
alphabetically, the last in corpus order, and the holder of a later document id
and a larger offset — so BM25 score, semantic similarity, RRF score, canonical
rank, document length, section name, timestamp and corpus position would each
move it. It does not move.
`test_m212_a_fully_reversed_order_survives_assembly` reverses corpus order
entirely, so every adjacent pair contradicts the corpus.

**FACT — verified end-to-end over real fusion output.**
`test_m212_the_fused_ranking_reaches_the_prompt_unchanged` runs the real BM25
lexical route over the committed 259-chunk corpus, fuses it through
`reciprocal_rank_fusion` with the canonical ordering authority, and asserts
`prompt.chunk_ids == fused_ids`.

**FACT — there is no second retrieval or ranking mechanism inside context
assembly.** `test_m212_the_context_builder_imports_nothing_from_the_pipeline`
asserts the module's declared imports are exactly `{"dataclasses"}` — it cannot
reach `sample_rag.retriever`, `sample_rag.fusion`, `sample_rag.vector_runtime`
or `sample_rag.vector_index`, and cannot perform filesystem or network I/O.
`test_m212_no_retrieval_generation_or_evaluation_name_is_declared` asserts no
declared name contains `bm25`, `rrf`, `fusion`, `rerank`, `embed`, `vector`,
`faiss`, `deepseek`, `ragas`, `deepeval`, `promptfoo`, `generate`, `token`,
`budget` or `truncat`.

### 3.2 Canonical ids resolve to canonical text — proof

**FACT.** Each supplied id resolves to exactly its own chunk record, or to
nothing. `test_m212_each_chunk_id_resolves_to_exactly_its_own_chunk` asserts
the mapping for every id in its corpus;
`test_m212_resolution_returns_the_canonical_chunk_record_itself` asserts the
**whole** record — including `document_id` and the document-frame offsets
`docs/GENERATION_CONTRACT.md` §8.3 requires a citation to resolve to — rather
than an id/text pair;
`test_m212_every_committed_chunk_id_resolves_to_its_committed_text` joins the
resolved records against the suite's own `real_chunks_by_id` fixture over the
committed corpus, so the specification and the implementation do not share a
source of truth.

## 4. Context representation

### 4.1 Exact structure

**ENGINEERING DECISION — the `Prompt` artifact.** No authority defines its
fields (§1.2). Three, each the smallest thing an existing authority requires to
exist:

| Field | Type | Why it exists |
|---|---|---|
| `query` | `str` | `docs/architecture.md` §4 gives Assemble the inputs *"Ranked chunks, query"*; §5 gives `assemble` the argument. Infer's stated input is the assembled prompt alone |
| `context` | `str` | The assembled evidence — what *"Build the final prompt from retrieved evidence"* produces |
| `chunk_ids` | `list` | Provenance. Makes `ALTM-ASSEMBLE-1`'s investigation executable: a diff against the retrieved chunk set needs identity, which a concatenated string does not carry |

Frozen dataclass, declaration order as listed — the convention
`docs/GENERATION_CONTRACT.md` §13.1 fixed for `GenerationResult`.

**ENGINEERING DECISION — what was deliberately omitted:** no `score`, no
`rank`, no token count, no budget, no timestamp, no separator marker, no
template, and **no `diagnostics` mapping**. `diagnostics` exists in
`RetrievalResult` and `GenerationResult` because a named authority requires
detail to be carried; none requires any here, and adding one would be
speculative surface. A score or rank in particular would be retrieval's
decision re-expressed as though assembly had a view on it.

**ENGINEERING DECISION — no serialization is defined.** Nothing persists a
`Prompt`. `docs/GENERATION_CONTRACT.md` §13.3's reasoning for
`GenerationResult` — a query-derived artifact existing for one request — applies
unchanged, and defining a serialized form for an artifact with no consumer
would fix a wire format before anything reads it.

### 4.2 Separators and boundaries

**FACT — no authority specifies separators, labels, document boundaries,
citation format, delimiters or metadata for a prompt.** Nothing in
`GENERATION_CONTRACT.md`, `architecture.md`, `altm.md`, `glossary.md` or the
registers states any of them.

**ENGINEERING DECISION — `CONTEXT_SEPARATOR = "\n\n"`**, and nothing else. The
context is chunk text joined by a blank line: **no label, no numbering, no
`[1]`-style citation marker, no document heading, no XML or Markdown delimiter,
no instruction and no system preamble.** Each would be text in the prompt that
no corpus chunk supports — the reasoning `docs/GENERATION_CONTRACT.md` §15
applied when it refused a free-text `citations` field alongside
`supporting_evidence`. Attribution is carried by `chunk_ids` in resolvable
form, not by markup invented here.

**Why a blank line rather than a newline.** The assembly must be **reversible**
for `ALTM-ASSEMBLE-1`'s diff to be exact. `sample_rag/generator.py` makes the
same claim for its `STATEMENT_SEPARATOR = "\n"`; a blank line holds under a
weaker precondition — it survives any corpus whose chunk texts contain no blank
line, including multiline chunks.
`test_m212_assembly_is_reversible_over_the_committed_corpus` **checks the
corpus property rather than assuming it** (no committed chunk contains a blank
line — in fact none contains a newline at all), and
`test_m212_a_multiline_chunk_does_not_split_into_two_blocks` shows why `"\n"`
would have been unsound.

**FINDING — this sprint performed no prompt engineering.** No system prompt, no
instruction text, no query rewriting, no answer-formatting strategy, no
hallucination-prevention wording and no evaluation prompt exists in the change
set. Prompt optimization is **M2-15**.

### 4.3 Provenance

**FACT.** `chunk_ids` carries the repository's canonical `chunks[].id` —
the identity **M2-04** fuses on — positionally aligned with the blocks of
`context`. `test_m212_chunk_ids_are_aligned_with_the_context_blocks` asserts
both halves: the ids are the supplied ones, and block *i* is the text of chunk
*i*. The full chunk record returned by `resolve` retains `document_id` and both
document-frame offsets, so a future `SupportingEvidence` remains constructible
without a second lookup.

## 5. Empty retrieval, missing ids, duplicates

### 5.1 Empty retrieval

**FACT — no repository authority defines an empty-retrieval policy at this
seam.** `docs/GENERATION_CONTRACT.md` §9.3 defines `Abstain` for the
*Generator*, and §20.2 records the abstention predicate as an implementation
decision belonging to the Generator.

**ENGINEERING DECISION.** `assemble([], query)` returns `Prompt(query=query,
context="", chunk_ids=[])` — the smallest deterministic behaviour, compatible
with the `Prompt` representation, and total: no branch, no sentinel text, no
`None`. An empty context is exactly true about an empty retrieval.

**FACT — no abstention logic was moved into M2-12.**
`test_m212_the_empty_retrieval_makes_no_abstention_decision` asserts the
artifact carries no outcome field and the empty context carries no abstention
text — an implementation that started deciding here would have nowhere to put
the decision. Whether an empty retrieval becomes an abstention remains upstream
and downstream of this stage.

### 5.2 Missing chunk id

**FACT — no repository authority defines missing-id behaviour at this seam.**

**ENGINEERING DECISION.** `resolve` raises `ContextAssemblyError` naming the
id. Reasoning from authority: returning a shorter list would drop evidence
silently, which is precisely `docs/architecture.md` §4's named Assemble-stage
failure (*"Retrieved evidence correct but dropped during assembly"*) and what
its responsibility (*"without silent truncation"*) forbids; substituting a
chunk would break identity; a placeholder would put unsupported text in the
context. **Raising is the one behaviour that neither drops silently nor
invents.** No fallback retrieval mechanism of any kind was introduced.
`ContextAssemblyError` follows the repository's existing named-error convention
(`ChunkConstructionError`, `DocumentConstructionError`,
`VectorIndexCompatibilityError`).

### 5.3 Duplicate chunk ids

**FACT — no repository authority defines duplicate semantics at this seam, and
M2-04 cannot produce one.** `rank_candidates` accumulates candidates into a
mapping keyed by chunk id, so a fused result is deduplicated by construction —
verified by `test_m212_the_fused_route_cannot_supply_a_duplicate_id` rather
than asserted.

**ENGINEERING DECISION — duplicates are preserved, not collapsed.** A duplicate
therefore says something about the caller, and collapsing it would silently
rewrite the supplied retrieval result into a different one. Preserving keeps
`resolve` length-preserving (`len(resolve(ids)) == len(ids)` on every
non-raising path), which is the property `chunk_ids` / `context` alignment
rests on. **No deduplication based on retrieval quality was introduced.**

## 6. Context-window policy

**FACT — no repository-defined context-window or token-budget policy exists.**
This is stated explicitly, as the sprint brief requires.

The concept is named three times and given a value nowhere:

- `docs/architecture.md` §5 — *"within budget"* (no value);
- `docs/architecture.md` §5 *Future Evolution* — *"Context-overflow handling
  under **real token budgets**"*, i.e. explicitly future work;
- `docs/glossary.md` — *"Context Window: the bounded input space available to
  **the generation model**"*.

**FACT — the reason it cannot exist yet.** A context window is a property of a
generation model. **No generation model is connected** — **M2-06** is not
implemented — so no budget value is derivable from repository state.

**ENGINEERING DECISION — the complete ordered context is preserved; nothing is
truncated or dropped.** This is what `docs/architecture.md` §4's responsibility
(*"Fit within context window without silent truncation"*) and named failure
mode (*"Retrieved evidence correct but dropped during assembly"*) require of
the stage, and it is available precisely because no budget is defined.

**No token-budget heuristic, model-specific limit, relevance-based truncation,
score-based chunk dropping or dynamic top-N selection was introduced.**
`test_m212_a_large_context_is_not_truncated` assembles a 1,000,000-character
context whole; `test_m212_nothing_is_dropped_or_truncated` asserts the exact
character arithmetic; and no `token`, `budget` or `truncat` name is declared
anywhere in the module. **The missing policy was not converted into a new
retrieval-quality mechanism.**

## 9. Findings and unresolved questions

**FINDING F-1 — no orchestration layer was created, deliberately.** The
repository's only retrieval→generation caller is `scripts/cli.py`, whose chain
is `parse -> load_corpus -> Retriever.retrieve -> Generator.generate ->
serialize`. It **does not use fusion at all** (it runs the lexical route
directly), and its generator consumes `RetrievalResult`. Wiring `RRF →
ContextBuilder → Generator` into it would have changed that path's retrieval
route *and* its generator input — neither of which is this sprint's to change,
and the second of which is barred by a frozen contract. Per the sprint brief's
Phase 2, M2-12 is therefore kept at its **independently testable seam**, and
`test_m212_no_pipeline_module_imports_the_context_builder` records structurally
that nothing was rewired to reach it. **The Context Builder has no runtime
consumer until M2-06.**

**FINDING F-2 — `architecture.md` §5's Context Builder row still reads
*Current Milestone 1A*.** The row is already flagged in that document as a
known residual divergence — *"No P3.7.3 authorization covers this row, and
